# The live session

This page covers a night at the table: what is durable, how a browser hears about a change, how a fight is started, ended and carried across nights, how the recap is assembled, and what a player may know about a fight in progress. Which rows an actor may reach is [Visibility](visibility.md); where a hit point lives is [Characters](characters.md); the runner's atoms and stream hook are [Web data](web-data.md).

## Durable state, and a doorbell for fan-out

Live state is written straight through to Postgres, transactionally. There is no in-memory copy of a fight, no write-behind and no cache: the promise that matters is the one kept through a crash mid-combat, and a four-hour session is on the order of a thousand writes. Do not add a cache; measure first.

The fan-out carries no data. `apps/server/src/live/LiveEvents.ts` publishes `{ sessionId }` and nothing else, and every subscriber re-reads the log through the ordinary SQL predicate when it rings. That buys three things: visibility stays in SQL, so there is no in-memory `filter` to forget; a dropped notification self-heals on the next re-read from the same cursor; and reconnect is not a separate code path, because catching up and tailing live are one query.

The `PubSub` is `sliding`, so a frozen tab costs latency rather than server memory. In-process fan-out is the one hosting constraint: one server process per live session. Swapping this module for Postgres `LISTEN`/`NOTIFY` lifts it with no schema change.

## The reconnect contract

Any live client must implement this against `GET …/runs/:runId/events` (`handlers.ts`, group `live`):

- Every event carries `session_event.seq` as its SSE `id:` line. `HttpApiSchema.StreamSse` is given the codec in `events` mode, not `data` mode; `data` mode hard-codes the id to `undefined` and the name to `message` (`packages/api/src/SessionEvent.ts`).
- Resume with `?since=<seq>`, exclusive. The derived client issues a plain `fetch`, which does not resend `Last-Event-ID`; the header is honoured too, for a native `EventSource`.
- Heartbeats carry no `id`, so a quiet connection never overwrites the client's cursor. The interval is `LIVE_HEARTBEAT_SECONDS` (`Config.ts`, default 20, under what an idle connection survives through a proxy).
- `GET …/log?since=` is the same query over a non-streaming transport.
- Authorization happens before a stream exists, so a denial is a JSON 404 rather than a failure event inside a 200.

A level visit's lines have a stream of their own, `GET …/sessions/:s/visits/:visitId/events` (`live.visitEvents`), under the same contract: the same replay-then-tail (`logStream` in `handlers.ts`, one implementation for both), over the night's lines naming the visit (`session_event.level_visit_id`). It is a second endpoint rather than a run stream bent to carry a visit, because a visit is not a fight and has no run to key on.

`seq` comes from one global sequence (`session_event_seq`), not `max(seq)+1` per session: a cursor only has to increase. It is `integer` (`0081`), so it reads as the wire's number. `payload` is the human-legible remainder, not state; a client re-reads rows rather than applying it. The hit-point, death-save and condition lines are the declared exceptions (`SessionEventPayload.ts`, which the server writes them through): the runner's _Rolls_ dock prints them, and nothing applies them.

## Modelling decisions

- The turn marker is `encounter_run.active_combatant_id`, a pointer, not an index. Adding, removing and rerolling reorder the list, after which an index silently names a different creature.
- There is no `player_view_enabled`. `encounter_run.visibility` is the share switch and `combatant.visibility` is hide-from-players. Both default to `dm`.
- Hit points reaching zero delete nothing and advance no turn. _Next turn_ then passes over an NPC row at zero, and never over a PC row, which still takes its turn for death saves (the captain's call); healing a monster above zero gives it its turns back. The conditions zero brings are the server's, applied by `vitals.ts` in the statement that moves the hit points, on both copies, for every path that moves them (a hit, the DM's typed total unless the same patch names its own conditions, the seat's delta, a natural 20, a rest): dropping to zero ends `Concentrating` for any row, and a PC falls `Unconscious`; a PC healed off zero loses `Unconscious`. Only the crossing writes, so they stay reversible: the DM toggles either back as any condition, and a further hit at zero leaves the toggle alone. An NPC gets no `Unconscious`; at zero it is out, which the number already says. The `combatant-damaged` line keeps the hit points before the hit, which the clamp loses, the `conditionsAdded` and `conditionsRemoved` the crossing wrote (as do the `combatant-updated`, `death-save` and `character-updated` lines that moved them), and the save's DC (`concentrationDc`, `packages/api/src/Concentration.ts`) when a row holding `Concentrating` took damage and is still up; that DC is noted, not acted on, so the condition stays until the DM clears it.
- Death saves are `death_save_successes`/`death_save_failures` on the combatant and the character (`0085_death_saves.ts`), written through by `vitals.ts` like a hit point, and drawn as `Combatant.deathSaves`, `null` for an NPC. The rules run in the statement that moves the hit points: a hit on a PC already at zero is one failure, two when `CombatantDamage.critical`, and a stable PC (three successes) who is hit starts dying again with its successes back at zero; any healing from zero clears both (the DM's typed total too); dropping to zero adds nothing; both stop at three. The DM's dots (`POST …/combatants/:id/death-saves`) set them; the DM's roll (`…/death-save-roll`) sends the face the browser rolled and the server applies `deathSaveRolled` under the row's lock, a natural 20 being one hit point and both cleared. A roll for an NPC, a PC above zero, or one with three of either is `Conflict`. Each appends a `death-save` line under the combatant's visibility. A seed copies the character's counts and a resume the combatant's.
- A combat encounter's fight opens rolling initiative (`encounter_run.phase = 'initiative'`, `0066_initiative_phase.ts`): every `combatant.initiative` is null and nobody is up, which `encounter_run_nobody_up_while_rolling` holds. `begin` (_Start round N_) is refused while any row, hidden ones included, has no number, and puts the marker on the first row that takes a turn; `reroll` goes back to the phase keeping every number and the round, so the DM changes only what changed. `nextTurn` and a hand-set marker are `Conflict` in the phase. `begin` and `reroll` are `Conflict` for a scene that is not a fight.
- `combatant.initiative_bonus` is snapshotted at seed time through `initiativeBonusOf` / `statBlockInitiativeBonus` (`packages/api/src/Initiative.ts`, shared with any client that rolls for somebody). It is "roll for them"'s modifier and the first tiebreak: `initiativeOrderKeys` orders by initiative, then bonus, then PCs before NPCs, then `created_at`, then `id`, with rows that have no number last.
- `combatant.initiative_set_by` (`dm` | `player`, null exactly when there is no number) decides whether a player may still change their own number. Every DM write stamps `dm`; `PlayerTable.setInitiative` stamps `player` and is refused (`Conflict`) once the DM has written one, so the DM's number always stands and the DM can always overwrite the player's.
- A combatant's side is `combatant.side` (`party` | `foes`, `0100_combatant_sides.ts`), apart from `kind`: `kind` says what a row is (a `pc` makes death saves, an `npc` at zero is out), `side` whom it fights for. A seat seeds `party`, a roster line its own `encounter_creature.side` (default `foes`), an add by hand its payload's or its kind's (`sideOfKind`), and `resume` copies it; the DM turns one with the ordinary update. It picks the edge a token starts on, the runner's badge and hostiles count, and which targets `npcTurnOptions` marks `ally` (an area's placements list the allies they catch); the legality rule refuses nothing on its account, and only Hob's fight toolkit keeps a monster off its own side ([Hob](hob.md)). No player read selects it; the one thing a player can infer from it is a party-side token staying on the board while hostile tokens are hidden.
- A combatant snapshots every displayable field at seed time; `character_id` / `creature_id` / `npc_id` are `on delete set null` and grant no reach. A roster line naming a member of the Cast (`encounter_creature.npc_id`, count one) seeds a combatant with that `npc_id`, the NPC's name, its sheet's armour class and hit points when the sheet has them and else the stat block's, and the line's `creature_id`: the stat block it fights as, which is all `npcTurnOptions` reads. Its subtitle is the creature's size and type, as any monster's, never the NPC's role. Archiving the NPC leaves the combatant as it is, and a roster line naming an archived NPC still seeds. No player read joins `npc`, `npc_sheet` or `npc_prep` through it (`cast-npc-combatants.test.ts`). The one live field is `portrait`, and it is reached through the character's seat, not the pointer (`seatedPortraitColumn`, [Characters](characters.md), _The portrait_). A retired seat takes it off the row. `encounter_run.encounter_name` is snapshotted too: it is what the fight was called that night, not what the template is called now.
- Hob's autopilot is `encounter_run.hob_autopilot_driver` (`0099_hob_autopilot.ts`), written through the creator's run update. Null is off; a value is on and names the one runner tab that drives, so the switch is also the lease: another tab of the DM's says the fight is driven elsewhere and taking over writes its own id. There is no heartbeat or expiry, so a closed tab leaves it on with nobody driving until a person takes over or turns it off. Turning it on or taking over is a `Conflict` on an ended fight; turning it off never is. Each change is its own `run-updated` line, logged `dm` whatever the fight's Share, apart from the rest of the patch. _Next turn_ takes an optional `expectedActiveCombatantId` and is a `Conflict` once the marker is on somebody else, so two drivers advancing from one creature's turn cannot skip the next one's; a repeated `requestId` still answers the run unchanged first. `hob-autopilot.test.ts` holds the switch, its log line, `resume` and the guard. The loop the switch turns on is the runner's ([Hob](hob.md)), and it meets the rest of the fight only through the endpoints a press uses: a turn's pending saves hold it until the DM enters them, an undo (only ever the run's latest kept turn) pauses it, and since `resume` drops the switch, a carried fight's saves lapse at the carry and the next night starts with autopilot off.
- Every fight has a board: `encounter_run_board` (`0058_encounter_run_boards.ts`), one per run. `start` copies the level visit it borrows or the encounter's level onto it (below), or, for an encounter that names none, writes the plain grid (`BOARD_COLUMNS_DEFAULT` by `BOARD_ROWS_DEFAULT` at 5 ft, no level); `resume` copies the predecessor's. So an edit to the level is the next fight's and never a running or finished one's, as `encounter_name` is, and a token's square keeps its meaning. Every board is drawn on itself, `BOARD_CELL_PX` a square with no offset (`packages/api/src/Board.ts`); whether its lines show is the runner's own _Grid_ switch, stored nowhere. It is its own table because a player's recap reads every `encounter_run` column but the DM's Hob switches (`playerRunColumns`). `GET …/runs/:r/board` (`RunBoards.forRun`, `repo/RunBoards.ts`) is the creator's alone; the runner draws it open, as the canvas behind its panels at desktop widths ([Web screens](web-screens.md)). A player sees it only on the live table, while the DM shows the map (below).
- A combatant's token stands on a square of its fight's board (`combatant.board_column`/`board_row`, `0064_combatant_positions.ts`), both `null` while it is off the board. Every token starts on the board, so the DM drags rather than places: `start` stands a party member on its seat's token when the fight borrows a level visit, and a roster creature on its placed spot (`encounter_creature_spot`) when the board has that square, a token may stand there and no creature already does; everyone else goes down their side's edge, the party's on the left and the foes' on the right, each column from its middle row outward, and `Combatants.create` puts one added by hand on its side's next free square (`startingSquares`, `packages/api`); a full board leaves the rest off it, and seeding writes no `combatant-moved` line. `POST …/combatants/:id/move` is the DM's write (place, move, or `position: null` to take it off), checked against the fight's own board, idempotent on `requestId`, and refusing no distance or turn; a seated player moves their own token through the table's own write (below), and both take the square check and the feet from `repo/moves.ts`. A move by the combatant holding the marker while the fight takes turns adds the feet it walked to its `feet_moved`: on a level the walk `pathCost` finds over the fight's copy (round walls, shut doors and blocking props, difficult terrain at double, diagonals by the campaign's `diagonal_rule`), on the plain grid `feetBetween` under that rule, and straight for a DM's drop no walk reaches; placing, taking off, an off-turn move and the initiative phase count nothing, and over-speed is not refused. Its `combatant-moved` line is shared only while a player's board shows that token (`tokenShown`, `repo/liveTables.ts`). `resume` copies positions with the rest of the row. The live table's board is the one player read that selects them.
- A turn's spending is on the fight's row (`0086_turn_economy.ts`, decision D2 of 2026-10-02, which leaves the sheet's D6 standing; since the maintainer's decision of 2026-10-07 a player reads and ticks their own row's, below): `action_used`, `bonus_used`, `reaction_used` and `feet_moved`. The DM ticks the first three with `POST …/combatants/:id/turn` (absolute values, idempotent on `requestId`, logged `combatant-updated` as `dm`), on any row, because a reaction is spent on another's turn; `feet_moved` has no hand-set write, only `move` adds to it. `freshTurn` (`repo/liveTables.ts`) clears only the row the marker lands on, in the same transaction as every write that moves it: `nextTurn`, `begin`, a hand-set marker that changes who is up, and removing whoever was up. `resume` copies them, so a fight carried mid-turn picks up where it was. The player's table selects them for the asker's own row alone, as it does that row's armour class.
- A monster's spending over the fight is on the same row, the creator's alone too (`0093_combatant_resources.ts`): `legendary_spent`, `recharge_spent` (the keys of recharge abilities waiting on their roll), and `uses_spent` and `slots_spent` (key to count, a key with nothing spent absent). The row holds what is **spent**, never what is left: the stat block says how many (`npcLimits`, `packages/api/src/NpcResources.ts`, whose `featureKey`, `spellKey` and `slotKey` are the keys), so a fresh row is zeros, `start` seeds nothing and no maximum is snapshotted, which would mean reading the creature through `creature_id`. `freshTurn` zeroes `legendary_spent` with the turn's ticks, as the SRD regains legendary actions at the start of the creature's turn; recharges, uses and slots stay. The DM sets them with `POST …/combatants/:id/resources` (absolute values, a zero count dropped, idempotent on `requestId`, logged `combatant-updated` as `dm`); keys are not checked against the stat block, and a PC's row is `Conflict`, its resources being the sheet's. `resume` copies them. No player read selects them.
- What a monster may do now is `npcTurnOptions` (`packages/api/src/NpcTurnOptions.ts`), the one reading of the rule: code lists what is legal and a chooser (the DM, or Hob's `proposeNpcTurn`) picks by option `id`; a chosen turn is checked by `npcTurnCheck` beside it, which asks the options again before each step on the fight the steps before it leave (a Dash's extra speed is granted there, since the options give speed less feet moved). It reads the creator's rows, the board under the campaign's `diagonalRule`, the stat blocks and the spell rows, never the database, so the runner and the server answer alike. The server reads it for whoever is up in `repo/TableFight.ts`, the creator's whole read of a fight, which also resolves the stat blocks' spells by name (`Spells.named`: the bundle's row first, then the creator's Library, then a share); the runner reads no spells yet, so its options leave them out. Turn economy, recharges, uses, slots and legendary actions come off the row against `npcLimits`; targets and area placements come from the stat block's structured `reach`, `range` and `area` ([Corpora](corpora.md)); what a block lacks the data for is put in `omitted` with a reason rather than guessed. On a level it offers only targets the creature sees past less than total cover, each with its `cover` and `unseenByTarget` (advantage), lists the rest in `sight.hidden`, centres a point area only on a creature it sees, and gives as movement the squares a walk reaches within its feet; `npcTurnCheck` counts a move's feet by `pathCost` and carries each aimed target's cover and sight to the keep (`aims`). A wall through a square's centre (a half-square wall, a slant along a square's diagonal) never traps a token standing on it: `movementCost` ignores a wall that only touches the centre a step leaves, so the token steps off every way the wall does not run along, while a step into such a square is still blocked. Its tests run on real SRD blocks checked in as `packages/api/src/fixtures/srd-turn.json`, which `srd-turn-fixture.test.ts` holds to the import, and `npc-turn-options-corpus.test.ts` runs every SRD monster through it.
- Fog of war is the board's too: `encounter_run_board.fog_hidden`, the squares under fog as `row * board_columns + column`, and `fog_start`, what _Reset_ puts back (`0087_run_board_fog.ts`). A fight starts clear, so `fog_start` is empty until fog is authored in prep. `PATCH …/runs/:r/board/fog` (`RunBoards.updateFog`, creator proof) applies at most one of `revealAll`, `coverAll` and `reset`, then `hide`, then `reveal`, idempotent on `requestId`; a square off the board is a `Conflict`. Its `board-fog-updated` line is shared while the board is shown (`boardShown`), so the players' doorbell rings. The DM's reads are never narrowed by fog.
- An area template is the board's working surface, not the fight's record (`0090_run_board_area.ts`, `run-area.test.ts`): the `area_*` columns on `encounter_run_board` hold one sphere, cone, line or cube, its size in feet, its origin square and, for a cone or a line, the square it points at. `PUT …/runs/:r/board/area` (`RunBoards.setArea`, creator proof) pins one, replacing what was there, or clears it with `area: null`, idempotent on `requestId`; a square off the board or a template `areaSquares` puts on no square is a `Conflict`. Its `board-area-updated` line is shared while the board is shown. `EncounterRuns.end` and the night carrying a fight both clear it (`clearArea`, `repo/liveTables.ts`), and `resume` does not copy it. The board keeps no history, but each pin and clear appends a `board-area-updated` line carrying the template, which the DM's run log shows as a line; no recap or player read uses that payload.
- A fight on a level plays on its own copy (`0109_level_fights.ts`, `repo/levelFights.ts`, `level-fights.test.ts`). `encounter.level_id` names one of the campaign creator's own levels, held by two keys (the level's `(id, account_id)` and the campaign's `(id, creator_account_id)`), and `Encounters` answers any other as `NotFound` before writing; deleting the level sets it `null`. `start` copies the level in one `insert … select` per table inside its transaction, holding the level `for share` from the lookup on, so a save or a delete in flight waits and the copy is one whole version; a level gone by then (or a board insert that copies nothing) leaves the fight on the plain grid. A fight that borrows a level visit copies the visit instead, live state and all ([Starting](#which-board-a-fight-starts-on)). The board row takes the level's size, scale, `ambient` and `floor`, so tokens, fog, areas and effects land on the squares the level is drawn on; `encounter_run_wall`, `_prop`, `_light` and `_region` take its parts. `resume` copies the predecessor's copy, doors and lights as left. Editing or deleting the level never moves a fight. Three things are live: a wall's `door_state` with `revealed` (a secret door the DM has shown the table), a light's `lit`, and a region's `revealed` (a secret trap or hazard the DM has shown the table, `0112_run_region_reveal.ts`). A locked door is a closed one, so locking an open door shuts it. `PATCH …/runs/:r/board/doors/:wallId`, `…/board/lights/:lightId` and `…/board/regions/:regionId` (`RunBoards.updateDoor`, `updateLight`, `updateRegion`, creator proof, idempotent on `requestId`; a seated player or a stranger is `NotFound`) write them through in one transaction and append `board-door-updated`, `board-light-updated` or `board-region-updated`, whose payload says which kind of door and what it was and became, or which preset the light matches (`SessionEventPayload.ts`), so the log can print "A door was locked" or "A torch was lit"; there are no room names to say where. Tokens start, and one added by hand lands, only where a creature may stand (`standable`).
- Party vision is written through too (`party_sees`, `party_seen`, [Visibility](visibility.md)): `refreshPartyVision` (`repo/levelFights.ts`) runs in the transaction of every write that can change it, after the write: `start` and `resume`, a combatant added, removed, moved (the DM's, a player's own, a kept Hob turn's) or put back by an undo, a door opened, closed, locked, revealed or hidden, and a light lit or snuffed. It locks the board row first, so two writes in one fight compute one after the other. A seat leaving the table recomputes it too: the owner or the creator retiring the seat (`Party.leave`), the creator removing the player (`revokeMemberAt`, also behind an invite's withdrawal) and the owner deleting the character (`Characters.removeOwn`) each find the live level fights the character stands in (`levelFightsOf`) and refresh and ring each in their transaction. A move recomputes the vision before it decides whether its own line is shared. A door's line is shared only for a door touching a square the party has seen, while the table is shown the board, that opened or shut with no lock in it: a plain door, or a secret door revealed before and after. Its finding or hiding and any lock stay the DM's line, since the table reads a locked door as closed. A light's line is shared only for one standing on such a square; a region's is always the DM's. When the write's own line is the DM's but what the table draws changed (the vision moved, a seen secret door or region was revealed or hidden, a seen door the table knows opened or shut, a creature the party saw walked out of sight), a contentless shared `board-vision-updated` rings the players instead. Not recomputed: a sheet's darkvision changing mid-fight, which the next such write picks up. The refresh reads the whole copy and runs `partyVision` on every such write, so on the largest levels it is the costliest part of a move.
- Cover and sight on a level are one rule (`LevelRules.ts`, `levelSight` in `LevelGeometry.ts`), read over the fight's copy as the table knows its secret doors (`tableSight`) by the DM's runner, `npcTurnOptions` and the keep. Cover is the DMG corner rule (`cover`): half adds 2 to the AC an attack rolls against, three-quarters 5, and total cover means no target. A wall that only ends at a creature's corner gives no cover (each corner is drawn from further inside its square than a sight segment runs past its end), and a low wall screens with half cover as a crate does, through the same rule for every reader. A creature sees a target when a line from its centre reaches the target's centre or a corner past what stops sight and the target is perceived there: lit dim or bright, or within its darkvision and not magically dark; blindsight within its reach past walls alone, truesight past heavy obscurement and in magical darkness. Senses are read off the stat block (`sensesOf`, a sense with no readable distance counted as none and listed), a party member's darkvision off its sheet. Attacking a target the attacker cannot see is at disadvantage and being attacked by one the target cannot see is at advantage, combined with long range by `combineModes`. The DM's attack applies all of it and says so on the result card and the target frame (`run/levelRules.ts`), and refuses a target in total cover with a toast; the DM can still roll a line with no target. A seated player's attack applies cover on the server, which resolves it (`Rolls.create`): from the attacker's square over the fight's whole copy, DM-only props included, half or three-quarters cover is added to the AC the to-hit is resolved against and kept as the roll's `targetAc`, and any aimed roll at a target with total cover from them is a `Conflict` that says so and writes nothing. The player's target card says the cover (`Half cover: +2 AC`) from the party's view of the level alone (`playerCover`), and only when the party has seen every square of the rectangle the two squares span, so every wall and sent prop a line could cross is on the table; otherwise it says nothing, and the server's answer stands (a DM-only prop can add cover the card never shows). Where the card can tell total cover the table does not send the roll. Sight's advantage and disadvantage are not applied to a player's attack: its d20 is thrown in the browser and the player picks the mode in the tray, and whether the target can see the attacker is the creature's senses, which the player is not told. An area reaches nobody with total cover from its point of origin (PHB, "Areas of Effect"), and half or three-quarters cover from there adds 2 or 5 to a Dexterity save against it (`saveCoverBonus`): a kept Hob area applies it (below and [Hob](hob.md)); the DM's pinned template is resolved by hand, so its banner sets apart who is behind total cover and says each caught creature's Dex-save bonus (`coverFromOrigin`, `run/area.ts`). On a level the runner's and the player's range are the squares a walk reaches (`reachableOnLevel`), the player's over the party's view, and a drag's ruler reads the walk, `No way there` when none does.
- A run is played by `encounter_run.mode`, its encounter's kind snapshotted by `start` (`0065_run_scenes.ts`). Only `combat` takes turns: `start` sets no marker for a conversation, a skill challenge or a hazard, and `nextTurn` refuses one with `Conflict`. Every kind still seeds the party and the roster, because a conversation that turns ugly becomes a fight through `escalate` (`POST …/runs/:r/escalate`), which keeps the same run, its combatants and its log, opens on rolling initiative at round 1 as any fight does, and is one way. Runs from before modes existed were all played as fights, and are `combat`.
- A scene keeps its state in `encounter_run_scene`, one per run and the creator's alone (`repo/RunScenes.ts`, `GET`/`PATCH …/runs/:r/scene`): the prep's tactic lines as tickable beats and its challenge, both copied at `start` so a prep edit is the next run's; the DM's attitude note, which sets no DC; and a hazard's `stages` and current `stage`, entered by the DM rather than parsed from the duration prose. Each field is refused outside its mode. Checks and saves are rows of `encounter_run_check`, logged and removed by the DM: exactly one of a skill or a save's ability, the total and DC when there were numbers (the DC defaults to the scene's own, a conversation has none), an outcome worked out by `checkOutcome` unless the DM called it, and for a hazard's save the stage it was made in, one per combatant per stage. Whether a skill challenge is won or lost is `challengeTally` over the log, never stored, so removing a mistaken check reopens it and a settled one refuses more. Scene writes append `dm` events (`scene-updated`, `check-logged`, `check-removed`), so no player doorbell rings for them. A fight logs no checks: a save made in one, such as concentration, is a roll of that `kind` (below).
- One live fight per session is `encounter_run_one_live_per_session`, a partial unique index on `(session_id) where ended_at is null`. `session.active_encounter_run_id` names it, is written only by starting and ending a run, and `session_active_encounter_run_fkey` is composite so a session cannot point at another session's fight. A player reads it null while the fight's Share switch is off ([Visibility](visibility.md)).
- Idempotency is `session_event_request_id_key`, a partial unique index on `(encounter_run_id, request_id)`; `requestAlreadyApplied` returns current state on a repeat.
- `created_at` does not order rows inserted by one transaction: `now()` is transaction start, so seeded combatants share a timestamp and two rows tied on initiative, bonus and kind fall through to `id`.

## Containment: `combatant → encounter_run → session → campaign`

`repo/visibility.ts` has a `Containment` chain the predicate walks recursively. Checking "the session is readable" and "the run is readable" as two separate questions is a hole: both are satisfied by a run in a different session of the same campaign, and the pair says nothing about whether the parent in the path is the parent of the row. Use `ensureNestedRowReadable` / `ensureNestedRowWritable` (and the `ensureNestedParent*` pair), which bind the foreign key. `apps/server/test/live-session.test.ts` pins every reachable path.

## Starting: the night and the fight are two acts

A session can start over roleplay with no encounter in sight, so opening a night and putting a fight on the table are separate doors sharing one client transition, `apps/web/src/session/start.ts`. `campaign/StartSessionDialog.tsx` opens a night and stops; `campaign/StartRunDialog.tsx` puts an encounter on the table, opening a night on the way only when none is open. A night can also exist before it is opened: the creator's Hob plans one (`proposeNight`), and keeping it makes the session, its checklist and any act it starts, unstarted and not pointed at, so nothing is live for the table. `plannedNightOf` in `start.ts` is the one reading of "planned" (the lowest-numbered night neither started nor ended): while no night is open the _Next session_ card shows it with its checklist, and either door opens it (points the campaign at it and stamps it) rather than numbering a new one past it.

`startSession` is three statements in order, and only the last is best effort: create the session (or take the planned one), point `campaign.currentSessionId` at it (fatal, because a session nothing points at is a night the DM cannot find again), then stamp `startedAt` under `Effect.ignore`.

`startedAt` therefore belongs to the night, not the fight: a running session with `activeEncounterRunId` null is the ordinary state of an evening. The campaign's button has three states computed once by `actFor` in `campaign/act.tsx`, asking the session and the run separately: `run` is undefined both with no night and with a night that has nothing on the table.

### Which board a fight starts on

The campaign's visits decide it (`EncounterRuns.start`, `level-visit-fights.test.ts`), since a fight on a level the party has been to is a fight in that dungeon:

- **The encounter's level has a visit on the table**: the fight borrows it. `encounter_run.level_visit_id` names the visit, and the board is copied from it (`borrowVisit`, `repo/levelFights.ts`): its size, scale, ambient and floor, every part with its door state, reveals and lights, its fog as the fight's starting fog, and what the party has seen; the party stands on its tokens. The visit row is held `for update` from the lookup to the commit, as a visit write holds it, so nothing lands between the copy and the borrow. `run-started` names the visit too, so the DM's visit stream hears it.
- **It has a visit that is not on the table**: a `Conflict` saying to put it on the table or reset it. A fresh copy of the level beside the visit would fork the dungeon. The web offers _Put it on the table_ instead of the start.
- **It has no visit**: a fresh copy of the level, as before visits existed. Placed creatures still start on their spots.

Everything else about a start (initiative, sides, visibility, Hob's autopilot off) is the same on every board.

### An encounter is played once

`EncounterRuns.start` refuses an encounter that has any run, live, ended or carried, on any night, with a `Conflict` worded as what to do instead (`playthroughOf`): go back to the fight on the table, pick up the carried one, or read the log. Continuing that one playthrough is not a start and is not refused: `resume` of its own carried run, and `escalate`, which keeps the same run. Encounters started several times before the rule simply count as played; no data changed for them.

It is a row lock and an existence check, not a partial unique index. `start` takes `for no key update` on the encounter row, so a second start of the same encounter (another tab, another night, where `encounter_run_one_live_per_session` cannot settle it) waits for the first to commit and then sees its run. An index needs a column meaning "the run that opened the playthrough", and none stays true: `continued_from` is `on delete set null`, so deleting the night that holds a carried chain's middle link would either fail on the index or reopen an encounter whose successor still stands. Deleting every night an encounter was played on does free it, because it then has no run. `play-once.test.ts` drives each case with real actors, including the race; a player never reaches the rule and is `NotFound` either way.

The browser offers no start that would be refused: see [Web screens](web-screens.md). Its one way to `resume` is `campaign/PickUpRunDialog.tsx`, behind an encounter's _Pick up_.

## Exploring a level: the visit

A level visit (`LevelVisit.ts`, [Data model](data-model.md#levels)) is the campaign's live state of one of its creator's levels, the dungeon between fights. The DM explores it with no fight on: stands a token on any square a token may stand on (no walk, no speed, as a miniature), opens and locks doors, reveals secret doors and regions, lights lights and paints fog. The players explore the visit on the table: each walks their own character's token (`table.moveOnVisit`, the maintainer's decision: players move their own, the DM moves any, with no hold switch), held to the walk a fight's move is over what the party has seen, with no speed, and refused as _No way there_ ([Visibility](visibility.md#levels)). The door, light, region and fog statements are the fight board's own (`repo/boardWrites.ts`, over `BoardTables`), so a door opens the same way on either. Every write, the DM's or a player's, is one `visitWrite` (`repo/LevelVisits.ts`): it holds the visit row `for update`, recomputes the party's vision over the visit (`refreshVisitVision`, the function a fight uses), and is one transaction.

- **Opening stands the party on the way in.** A level's `entry` region is the DM's overlay of where the party comes in; `open` stands the seats on its squares a token fits, in reading order, and the rest down the left edge. A seat that sits down while a visit is on the table (`Party.join`) stands on the first free entry square, else the left edge, and putting a visit on the table stands any live seat it has no token for; a character that leaves and sits down again is a new seat and a new token. A fight on the level ignores the entry, and no player read sends it.
- **Borrowed by a fight, and handed back.** A fight on the level starts from the visit on the table ([Which board](#which-board-a-fight-starts-on)). While it is live the visit is frozen, so the visit and the fight never both answer for the dungeon: every visit write is a `Conflict`, and so are putting another visit on the table (the maintainer's decision of 2026-10-22), taking this one off, and resetting it; the DM's read names the fight (`LevelVisit.fight`) and the stage is read-only under a banner to it; the player's table shows the fight instead of the visit. When the fight ends **resolved** (`EncounterRuns.end`, the one place a run resolves), the same transaction hands the dungeon back (`LevelVisits.handBack`): door states, reveals, lights and fog go from the fight's parts onto the visit's of the same id (`returnBoardState`), `party_seen` becomes the union, each live seat whose character stood on the fight's board stands there on the visit (a seat with no token gains one), the party looks again, and a `visit-returned` line, shared while the visit is on the table, tells the players' table to go back to it. A carried fight hands nothing back and frees the visit until it is picked up ([Carried](#a-fight-that-carries-across-nights)). A fight deleted with its night hands nothing back: its rows go, so the visit is unfrozen exactly as it was before the fight. A visit reset after a fight leaves the fight its copy and empties its pointer.
- **Logged only on an open night.** A visit outlives nights, so its writes are logged on whichever night is open (the campaign's current session, started and not ended) as `visit-*` lines naming the visit, and ring that night's doorbell after the commit. With no night open a write logs nothing and rings nothing.
- **Which lines are the table's** mirrors `0110`'s rules for a fight, and only while the visit is on the table: a token's move is shared when its seat is shared and the DM's fog does not cover where it stands; a door's when the party has seen it and it opened or shut with no lock in it (`doorTold`, the rule a fight's door uses); a light's when it stands on a seen square; putting a visit on or off the table (and resetting one that was on it) is shared. A region's, the fog's, a secret door's finding and a lock stay the DM's, and where the table draws something differently anyway (the vision moved, a seen region or secret door changed, fog came over or off a seen square, a token stood or went) a contentless shared `visit-vision-updated` rings the players' doorbell. The players' stream is the table's ordinary tick stream; the DM's stage hears everything on the visit stream.
- **Placed encounters are on the visit, not of it.** An encounter placed on the visit's level ([Data model](data-model.md#levels)) is listed on the DM's read and drawn on the stage, and its creatures reach a player only while the party sees their squares ([Visibility](visibility.md#levels)). A placement is an encounter write, so it is not frozen by a borrowing fight; on an open night it logs the DM's `visit-placement-updated` line on the campaign's visit of the level, and a contentless shared `visit-vision-updated` when the creatures the table sees there changed. Starting one plays it there, and it drops off the list, since an encounter is played once.
- **Idempotent without a night.** A fight's `requestId` is kept on its log line; a visit write may have no line, so the visit keeps its own ledger (`level_visit_request`), entered first in the write's transaction, so a late retry of an earlier drag changes nothing.

## Finishing: one write, and the server owns the rest

Every surface that ends a night goes through `apps/web/src/session/finish.ts`, which sends one `PATCH … { endedAt }` and nothing else. `finish.test.tsx` drives both callers (`run/EndRunDialog.tsx`, `campaign/FinishSessionDialog.tsx`) against one stub server and compares the requests; a third surface should extend that file.

The rest is `repo/Sessions.ts`, inside the transaction that stamps `ended_at`: `releaseIfFinished` clears `campaign.current_session_id`, and `carryLiveRun` ends a fight still on the table as `carried`, clears `session.active_encounter_run_id` and appends `run-carried`. Neither lives in a dialog, because a client that forgets one recreates a bug a second client never sees.

`campaign_current_session_id_fkey` (`0006_session_finished.ts`) makes a finished current session unrepresentable: it is composite over `session.is_open` (generated, `ended_at is null`) and a constant-true generated column on the campaign, so `(id, true)` has no row to match once the session ends. It is `deferrable initially deferred` because ending and clearing are two statements. Postgres refuses `on delete set null` on a key containing a generated column, so `Sessions.remove` clears the pointer itself. `repo/Campaigns.ts` answers `Conflict` to a campaign pointed at a finished session. `session-lifecycle.test.ts` pins the invariant against raw SQL as well as the repositories.

Ending a fight is not finishing the night. `EndRunDialog` defaults to the smaller ending (`resolved`); only its switch stamps `endedAt`.

## A fight that carries across nights

A night may finish with a fight on the table, and the fight continues into the next one as a second `encounter_run` row, never a reparented one: the predecessor keeps its night with `ended_reason = 'carried'`, and the successor points back through `continued_from`. The log is the assistant's memory, and a moved row's `run-started` event would stay filed under a night it no longer claims (`0007_run_carryover.ts`).

- `EncounterRuns.resume` (`POST …/sessions/:s/runs/resume { continuedFrom }`) copies the round, mode, phase, visibility, the map's two switches (never Hob's direct-write switch or its autopilot, which the DM turns on again for the night they are watching), provenance, the board with its fog (never its pinned area template), the scene with its log of checks, and every combatant. Combatant ids are generated in TypeScript before the insert, the only way the turn marker can carry: `encounter_run_active_combatant_fkey` refuses a marker naming another run's combatant, so `insert … select` could not remap it.
- Only a `carried` run may be resumed. A `resolved` one is a `Conflict`, not a 404: reopening it would put "resolved" in one recap and "resumed" in the next. Nor can it be started again, since an encounter is played once (above).
- `continued_from` cannot be a composite key: the only column both runs share is `session_id`, which would force them into the same night. Containment is `resume`'s job against `containedRowReadable`.
- `encounter_run_one_successor` stops two nights both continuing one fight; `encounter_run_reason_needs_end` keeps a live run from carrying a reason.
- A fight that borrowed a level visit (`level_visit_id`) is still in that dungeon: carrying hands nothing back, and the successor inherits the pointer and hands back when it resolves, once. Its board is the predecessor's, never the visit's as it stands on the night it is picked up. Between the nights nothing borrows the visit (the predecessor has ended), so the DM can explore or reset it; whatever the successor hands back overwrites what the DM did there. `encounter_run_level_visit_live` refuses picking it up while another fight is being played on the visit.
- The order of combatants tied on initiative does not survive a resume (fresh ids, one shared `created_at`). `carryover.test.ts` says so.

## The recap: assembled per read, never stored

`repo/Recap.ts` assembles `SessionRecap` from five sources through five existing predicates: the session, every run of the night with its combatants, all beats verbatim, ticked prep only (an unticked line is the next night's), and notes attached to an encounter one of tonight's fights was started from. Nothing is stored and no model is called in the read path. Which notes count is structural, not a timestamp window; a window is wrong whenever the DM preps at lunchtime.

A `RecapFight` is `run` plus two `RecapRunLink`s carrying the other run's session number and round, so a pause and its pickup are expressible from either end. Following `continued_from` grants no reach: the far run goes through `containedRowReadable` and comes back `null` when the actor cannot see it (`recap.test.ts`). Paused-versus-finished is `run.endedReason`, never a guess from `endedAt`; the round trap in telling one is in [Web screens](web-screens.md).

The creator's `RecapFight` also carries the run's checks and saves, oldest first, and for a scene that was not a fight its `scene`: the challenge snapshot, the last attitude and the hazard's stages, which `fightStory` counts the log against. The player's has no field for either.

It is a server-side repository because it has two consumers, the Chronicle and Hob's `sessionRecap` tool; composed client-side, the assistant would write a second version.

The whole record is one read: `GET /campaigns/:c/chronicle` (creator proof, `ChronicleNight`) and `GET …/chronicle/player` (any member, `PlayerChronicleNight`) answer every readable night, newest first, with its runs and beats and none of the per-night detail. They go through the same `nights` function in `Recap.ts` that a recap starts from, so a night in the list is the night its recap describes (`chronicle.test.ts` compares them for both audiences). A list that needs every night open must use it rather than a recap per night.

### The player projection is a second schema on a second path

`GET …/recap` takes the `CampaignCreatorActor` proof; `GET …/recap/player` answers `PlayerSessionRecap` to any member, from the same queries. Never a field filter over the DM's type: a leak then has to be written rather than caused by a forgotten flag. `PlayerCombatant` (`packages/api/src/PlayerRecap.ts`) is a union discriminated on `kind`, so the `npc` arm has no field for an exact total and the `pc` arm keeps exact hit points. `hpBand` is computed in SQL in `repo/playerCombatant.ts`, the only place the narrow projection is spelled, and the wide columns are never selected, so there is no number in memory for a decode to forget. Conditions come through whole; a per-condition rule would be a visibility judgement outside the predicate. A run is a `PlayerEncounterRun`, selected through `playerRunColumns`, which leaves out the DM's two Hob switches (how the fight was run, not what happened in it); otherwise it is narrowed only in which encounter it names: `playerRunColumns` gives a player the encounter's id and snapshot name only when they may read that encounter (Shared and Ready), and otherwise `null` and the kind of scene, "A fight" or "A skill challenge" ([Visibility](visibility.md)). A run that was not a fight has no `combatants` in the player's recap, as it had no order at their table; its checks are the creator's (`RecapFight.checks`). The player's table and Chronicle use the same columns, so the table's `fight.encounterId`, and with it the read-aloud the table shows, follows the same rule. The beats and the prep are not narrowed: they are already the shared rows by row-level predicate. A note is told as `PlayerNote`, the projection the player's Overview reads, because `Note` carries the creator's links.

## The player live table

`GET /campaigns/:c/table` answers `PlayerLiveTable | null` (`packages/api/src/PlayerLive.ts`, `repo/PlayerTable.ts`). `null` is the ordinary success; the 404 is kept for a campaign the caller cannot reach at all, because a banner's absence must not be indistinguishable from a table that is not yours. Everything narrower is an absence.

- Seat proof comes first and is an active `campaign_character` row, not `combatant.character_id`. A member with no seat gets `null`.
- The order is `you | ally | npc`. `you` and `ally` carry exact `hpCurrent`/`hpMax` and `deathSaves`: a party shares its numbers (the maintainer's decision of 2026-10-03), and an ally row exists only under a seat the asker may see, the same join that selects them. Only `you` carries `tempHp`. `npc` carries a band and never a number or saves. NPC armour class is never selected.
- `you` and `ally` carry the character's `portrait`, selected in SQL by `seatedPortraitColumn`, so it is exactly what the party read would give the same reader. `npc` has no field for one.
- `mode` says what kind of scene is on the table. A run that is not a fight has no order: only the asker's own rows are selected, for `seats`, and `order` is empty with `upNext` null. Nothing of the scene is on this read: its kind, the read-aloud through `encounterId` and the player's own rolls are all a player has of it (the captain's decision of 2026-09-25). `apps/server/test/player-scenes.test.ts` plants every scene field and reads the raw wire for it. The table draws the kind as a card in place of the initiative list, titled by its neutral name whatever the encounter (`play/SceneOnTheTable.tsx`), since the table never carries the encounter's name.
- The encounter's name is deliberately absent. A fight on the table may be something the DM has not said yet, so attachments key on `encounterId`.
- Each visibility switch takes exactly one thing away, fail-closed: an unshared session is `null`; an unshared run is the night with `fight: null`; an unshared combatant drops the row, and turns `upNext` from `visible` to `hidden` if it named it. That applies to a player's own row too.
- `fight.phase` says whether the table is rolling initiative. Initiatives may be null. Only `you` carries `initiativeBonus`, `initiativeSetBy` and temporary hit points, selected in SQL for the asker's own row alone; every hit point through `repo/playerCombatant.ts`, as the recap's are, so a monster's or a hidden seat's never reach the decode.
- `upNext` is `visible` with the row's id and name, `hidden` with neither when the marker is on a row the order lacks (a hidden creature, a seat the asker may not see), so the table can say something moves (the same decision), and `null` only when no marker is set, which includes rolling initiative and a run that is not a fight. The DM hid the creature, not the fact that the turn moved. The table's turn banner (`play/turnBanner.ts`) takes _up next_ from the player's own order, so it is the next row that player can see; on the hidden arm it names nobody next, because where the hidden row stands is not on the wire and the row after a guessed position would be a guess.
- The group's writes reach only the row `ownSeatedCombatant` allows in the campaign's current night, the asker's own character; any other row or asker is `NotFound`, as the read would be, and the DM, who holds no seat, writes through the runner. `PUT …/table/runs/:r/combatants/:id/initiative` is a player's own initiative, `Conflict` once the fight is not rolling it or the DM has written a number. `POST …/move` moves their own token to a square on their own turn while the DM shows the map, counting the feet as the DM's move does; it never takes a token off or puts one down from nowhere, and off their turn, while rolling or with the map hidden it is `Conflict`. On a level fight the square must also be reachable from where the token stands, step by step over the fight's copy (`partyPathCost`, `LevelFight.ts`): no wall, no door that is not open, no secret door the DM has not revealed, no blocking prop, no void, and only over squares the party has seen, the DM's fog taken out, ending at most one step into the dark beyond them ([Visibility](visibility.md)); otherwise it is a `Conflict` the table shows, in the same words whatever stood in the way. Only reachability is refused, not distance: `feet_moved` is counted by the walk and over-speed is still the runner's to say. The DM still places freely. `POST …/turn` ticks their own action and bonus action on their own turn and their reaction on anybody's, since that is when one is spent, logged `dm` as the DM's ticks are (the maintainer's decision of 2026-10-07). `player-initiative.test.ts` and `player-turn.test.ts` drive every refusal with real actors.
- The fight's board is `fight.board` (`PlayerLiveBoard`), a schema of its own: the board's size, scale, fog, pinned area and tokens, never the level's id. It is selected only while the run is shared and the DM has turned on _Share map_ (`encounter_run.map_shown`, `0067_run_map_sharing.ts`, default off), with the fight's own Share as its gate even for a creator reading their own seat. A token is a position selected beside a row of the order under `tokenShown`, so a row the order drops takes its token, an unplaced row has none, and while `hostile_tokens_hidden` (the map's _Hide from players_) is on no NPC has one though its row stays, unless it is on the party's side (`combatant.side`). Fog takes more: a creature under it loses its row of the order and so its token (`hiddenByFog`, `repo/liveTables.ts`), whether or not the map is shown, so turning _Share map_ off shows nobody what was under the fog. A party row the reader may already see through a seat keeps its row, name and numbers under fog, because the party knows who is in it, but loses its token; only the reader's own token shows over fog (`tokenShownTo`). The player's recap drops the same rows while the fight is live, in a carried run too while the last run of its chain is unended or carried and not yet resumed (`fightLive`), and once that last run ends any other way follows the per-row rule alone. The board carries the fogged squares as `fog`. It carries the DM's pinned area template as `area`, so a player sees it exactly while they see the board. Turning Share off and on again brings the board back as the DM left it. On a level fight the board carries `level`, the party's view of the level narrowed in SQL (`PlayerLiveLevel`, [Visibility](visibility.md)), and a creature outside what the party sees now is treated as under fog, row and token. The table draws it with the DM's level renderer in the party's view (`LevelBackdrop` with `party`, `play/PlayerBoard.tsx`). `player-board.test.ts` and `party-vision.test.ts` drive each gate with real actors.
- `visit` (`PlayerLevelVisit`) is the level visit on the table, narrowed as a fight's level is, while the night is open and no fight borrows it ([Exploring a level](#exploring-a-level-the-visit), [Visibility](visibility.md#levels)); its one write, `PUT …/table/visits/:v/tokens/:seatId`, walks the asker's own seat's token, and any other seat, visit or asker is `NotFound`.
- It is not gated by the creator proof: that gate is for a read whose player projection diverges from the DM's, and this read has no DM projection. A DM calling it gets the identical narrow answer, which is how "what will my players see" is one request.

The stream at `GET …/table/sessions/:s/events` is contentless: after the same authorization it emits `tick` events with a cursor and no payload, draining shared `session_event.seq`s and emitting an empty same-cursor tick when a share/hide mutation wrote no shared row, so the browser always re-reads the narrow table. The own-character roll log is `GET …/table/sessions/:s/characters/:characterId/rolls`; there is no broad player log. The one log-shaped field on the table is `fight.narration`: the last few `hob-turn-kept` lines of the fight, selected in SQL as only the `shared` ones (the keep decides that from the acting creature's visibility and fog at that moment, so hiding the creature later does not unsay a line) and none whose turn was undone. Each keep and undo rings the doorbell with a line at that visibility, so a table that heard the turn re-reads.

Rolls are browser-submitted, but for a kept Hob turn's, which the server rolls and files through the same insert (`fileRoll`; [Hob](hob.md)), `dm`, stamped with the turn, a monster's saving throw as `kind: save`; a party member's save against one is the player's, entered by the DM and resolved by the server, and lapses with the fight. Undoing such a turn leaves its rolls in place with `undoneAt` set. `POST /campaigns/:c/rolls` (`repo/Rolls.ts`) stores the faces the browser sent, stamps `session_event.character_id`, rings the same doorbell, and refuses a player roll with no active seat for that character or no shared current night. A roll takes the night's visibility, except that the DM's are `dm` (the maintainer's decision D4): one with no character always is, because its label may carry a monster's name, and `visibility: "dm"` keeps any roll to the creator, which only the creator may ask for. The read predicate already answers a `dm` row to the creator and the roller alone, on the list and by id, and its `roll-made` line takes the roll's visibility, so no player tick carries it, with one exception: a DM's roll the players' board draws (an attack between two creatures shared and not under fog, or an area, on a board shown to them; `tableSeesAct`, the test a kept Hob turn's narration is heard by) rings their doorbell with a `shared` line whose payload is the roll's id alone, and the roll itself stays the DM's. What the players then read of it is the table's `acts` (`PlayerLiveAct`), a distinct schema selected in SQL through `combatantShownTo` (`repo/liveTables.ts`, the same test a roll's pointers are read through): an attack only when both creatures pass, an area whenever the board is shown with its creature only when that passes, and never a label, total or armour class. A roll says what it was for (`kind`: an attack, its damage, a monster's save against a Hob-run turn, a death save, a concentration save, or `plain`), and the DM's may name who rolled and at whom (`combatantId`, `targetCombatantId`, each a combatant of the fight on the table, composite with the roll's run in `0089_roll_attack_log.ts`, else `NotFound`), the target's AC and an attack's `outcome`, which the browser worked out and the server stores without recomputing. An attack also says what it was, for the board to draw: `delivery` (melee or ranged, weapon or spell) on the to-hit and `damageType` on the to-hit and each damage roll, both closed vocabularies checked in `0102_roll_attack_delivery.ts` and worked out by one rule for the runner's strike and a kept Hob turn (`attackDelivery`, `damageTypeOf`, `packages/api/src/AttackDelivery.ts`: a spell's own attack type, else the band the target stands in, else the line's only reach or range). A line that cannot say leaves them null rather than guessing; a party member's sheet line has no reach or range as data, so the DM's strike with one files no delivery. A save for damage that went somewhere keeps the template on its first damage roll (`area`, `0103_roll_area.ts`, the board's own `BoardArea` as `jsonb`): a kept Hob turn's placement (`boardAreaOf`), or the template the DM had pinned when they rolled a line whose stat block gives it an area; like the combatant pointers it is the creator's to file, and a player who sends one is `NotFound`. A save with no damage dice files no damage roll and so keeps no area. A player may name combatants only as their own attack: from the combatant that is the character they roll for, in tonight's fight, at one their table shows (the read predicate below, so a hidden or fogged creature is `NotFound`); the server then resolves the to-hit against the target's AC, with its cover from the attacker on a level (cover and sight above), with the one verdict (`attackVerdict`) and keeps the outcome and AC itself, ignoring any the browser sent, because the player is never told a creature's AC. Anything else a player names is `NotFound`. On a roll a player may read, each pointer is narrowed in SQL as their order reads the row: through the combatant's own predicate and, while its fight is live, not hidden by fog (`hiddenByFog`), else `null`; the creator reads every pointer. `targetAc` reaches a player only when the target is a player character they may be told about, so a creature's AC stays the DM's; `outcome` is everyone's who reads the roll. `player-table.test.ts` and `rolls.test.ts` pin the projection, the ticks and the no-auto-seat boundary.
