# Web screens

Routing, the shell, the signed-out gate, the shape every screen copies, the authoring and filter conventions, and the traps in the Chronicle, the character sheet and the Hob panel. Read this before adding a route, a screen, a dialog or a filter box. Reads and writes are [Web data](web-data.md); tokens, layering and motion are [Design system](design-system.md).

## Routing: real paths

`apps/web/src/routes.tsx` is the whole route table and the one `createRouter`, on the browser history: every route is a path (`/campaigns/<id>`, `/join/<token>`), and a `#fragment` is only an in-page anchor. The app ran on a hash history to keep the invitation token out of access logs; the maintainer decided on 2026-09-23 that clean URLs are worth that, since an invitation is single-use. The API still takes the token in a `POST` body, never its own request line.

- Every non-file path must be served `index.html`. Vite's dev server and `vite preview` do it; a static host needs the rewrite `README.md` names, or a reload on a deep link is a 404. The router's `basepath` is Vite's `base` (`import.meta.env.BASE_URL`), so a subpath deployment is one setting.

- A bad id is a bad link, not a crash. Every branded id decodes in `params.parse`, which returns `false` for anything the product did not mint; the router rejects that candidate and keeps matching, and every legible level has a `$` splat child, so a truncated run link lands on its campaign. Do not throw: a throw becomes a `PathParamError` and a rendered apology.
- Every product route sits under the pathless layout route `_shell` (`shell/ShellLayout.tsx`); `/join/$token` sits under `_standalone`, the same shell without the Hob panel. A pathless id prefixes every child's id, so `useParams({ from })` and `RouteIds` say `/_shell/campaigns/$campaignId`, while `to`, `matchRoute` and `fullPath` are paths and do not.
- `remountDeps` is set on every route whose params name a different thing so nothing loaded for one survives into another. It remounts the leaf, never the layout. The campaign index deliberately has none; it is what everything else falls back to.
- A rendered `href` is the path under the basepath. An imperative absolute link goes through `router.history.createHref(router.buildLocation(…).publicHref)` resolved against `location.origin`, which is what carries the basepath; `buildLocation(…).href` does not. `campaign/InviteDialog.tsx` is the one caller; `routes.test.ts` pins the basepath and `campaign/invites.test.tsx` the whole link.
- `Link` spreads `aria-current="page"` on any prefix match and `activeProps={{}}` does not stop it. Nav items pass `activeOptions={{ exact: true }}` so the bar's own section rule decides what is lit (`navLinkProps` in `shell/AppShell.tsx`).
- In-page anchors are `<Link to="…" hash="…">`, so the anchor names its page and the router's `scrollRestoration: true` performs the scroll.

Testing: `src/test/renderRoute.tsx`'s `renderAt(path)` renders the real tree at a real URL on a real browser history, a fresh router and `RegistryProvider` per render, and must be awaited because the first match resolves inside a `Suspense`. Screens are not mountable on their own. `shell/AppShell.test.tsx` enumerates `Record<RouteIds<typeof routeTree>, string | undefined>`, so a new route does not compile until it has a URL, splats included.

## The shell: mounted once, two rows, one section

`shell/AppShell.tsx` draws a global row and a campaign row that exists exactly when the route names a campaign. `shell/ShellLayout.tsx` is its only mount, so the header, both rows, the bar's slot and the Hob panel are the same nodes across navigation; `shell/ShellLayout.test.tsx` pins that by node identity and fails if any other file imports `AppShell`. The two nav rows and, above any campaign, the per-screen bar share one sticky `z-chrome` stack, and `main` is a `@container`. The stack and `main` are one column of `HobFrame`, the app's full-height row; a docked Hob panel is the row's other column, so it narrows the bars along with the content instead of sitting under them.

- A screen reaches the shell at one point: `TopBar` (`shell/TopBar.tsx`), rendered first in the screen. Above any campaign it is portalled into a slot inside that sticky stack, the per-screen bar. **Inside a campaign there is no per-screen bar** (the captain's decision of 2026-09-23, from the Overview redesign): every campaign screen is a tab of one thing, the campaign row is the last chrome row there, and `TopBar` draws the same header in place, at the top of the content. The Overview, the creator's and a player's, is the one campaign screen with no `TopBar`: it is the campaign itself, so its `h1` is the campaign's name in its hero (below). A Shared World's screen is the one screen above a campaign with no bar, for the same reason: it is the world's Overview and its `h1` is the world's name in the same hero. It decides from the route, so no campaign screen can draw a bar its siblings lack; `shell/ShellLayout.test.tsx` walks every audited screen and asks where its `h1` landed. Nothing travels up as a prop, and the rows need no separately maintained `top` offsets. The header is `@taverns/ui`'s `PageHeader` in both placements (`placement="bar" | "content"`), so the title, the reserved lines and the wrap rule are one implementation.
- Screen actions are the header's (`TopBar`'s children), never a button right-aligned elsewhere in the body; a card's own verbs stay on the card. The way back to a parent screen is `BackLink` (a chevron and the destination's name, rendered into the router's `Link`), first in the header's actions; the campaign row's way home is the same component. On the creator's Overview the hero carries the campaign's management as outline buttons: _Invite player_, _Settings_ wearing the _Private_ / _Shared_ word (the prototype drops the word; the captain kept it), and _Campaign actions_; on a player's it carries their one verb, the peach _New character_. A Shared World's hero carries the peach _New campaign_ for every member (founding one is any member's act), and for its owner _Shared World settings_ and _Shared World actions_ (archive, delete) as outline buttons beside it.
- Every screen grows the document and the window scrolls, under the sticky chrome stack. A page is never bounded to the viewport with its scrolling handed to an inner container: a second scroller is where the wheel gets stuck, and it hides content behind a scroll box nobody sees. `sticky` is fine, and pins under the chrome by `--chrome-height`, which `AppShell` measures off the stack and publishes on the shell's column (the stack's height depends on the route). A modal dialog scrolling its own body is a separate case, and so is the Hob panel's thread. A chat on a page (`cast/RehearsalPanel.tsx`) is a transcript in the document with its composer `sticky` at the viewport's bottom, and keeps the newest line in view by scrolling the window to its end.
- "Nothing appears on both rows" is one value: `useSection()` in `shell/location.ts` answers a single `Section` and both rows ask it, so being inside a campaign and no global item being lit are the same fact.
- The campaign row wears `tabsTriggerVariants` (exported from `@taverns/ui` for this; do not copy the recipe); the global row is `navPillVariants`, kept beside it in `tabs.tsx`. An underline says which part of this campaign you are reading.
- Each row is its own `@container`: each runs out of room at a different width, and the question is whether this row fits. The page edge is the one question that is not a row's — every row and `main` ask `@container/app` on the shell's column (the frame less any docked Hob panel), so the nav rows and the content below them cannot pick different edges. **A container query resolves against the container's content box**, so a container that also carries the page padding makes every threshold inside it mean "that, plus 64px"; the rows put the padding on a box inside the container for this reason.
- The campaign name gives way whole (`hidden` under the row's `@3xl`) and the chevron keeps `min-w-4` as a floor so the way home survives; its `aria-label` carries the name plus "home" for the state where the name is not drawn.
- The campaign row sources itself: the way home from the route, the name from `campaignAtom`, and, for a creator only, the session badge from `campaignNightAtom` (the campaign, its open session and its live run, without the rest of the view). `campaign/campaignRow.test.tsx` reads the destinations out of the rendered row and visits each.
- Every row has a fixed height, written down in `AppShell.tsx`: 44 global, 46 campaign, 76 per-screen bar, 40 tab strip. This is a decision, not a minimum: the bar measured 61 / 89 / 141 between sibling tabs when it grew with its contents, so the content jumped as a DM changed tab. Inside a campaign the chrome is the two nav rows and nothing else, so every tab's content starts at one y at every width. The header reserves the subtitle line whether or not a screen has one and, from the `@4xl/app` container (896px) up, never wraps, so whatever follows it starts at one y across a campaign's tabs too. Below it the actions take their own wrapping row and the header's height follows the screen: at 390 and 760 the unwrapping row drew the Cast's controls on top of one another, and wrapping keeps the tap targets whole. A screen whose controls do not fit one row above the breakpoint simplifies its composition (the Cast's _Add from Library_ draws only its icon between `@4xl` and `@7xl`). The delivered `base.css` gives every `p` a 12px bottom margin, which is why the subtitle carries `mb-0`. `shell/ShellLayout.test.tsx` pins the classes; the pixels are in [Measuring the shell](#measuring-the-shell).
- The campaign's one verb — _Start session_ / _Start an encounter_ / _Back to the fight_ — is the peach press at the right end of the campaign row, on every tab, as the redesign draws it (`CampaignAct` in `shell/AppShell.tsx`, sourced from the route like the rest of the row). It is the creator's only, it is absent on the fight it would send you back to, and it is absent on three screens whose own peach is their next step: one encounter's page, whose _Run_ is the same `run` aimed at that encounter, and two flows whose way out is _Cancel_ — the encounter builder (new and editing) and the campaign's character create form. The Overview's cards draw no second one: the live banner carries _Finish the night_ and leaves the way back to the row. It was once moved off this row because it overflowed at 760; the captain chose the row anyway, so the row collapses to make room instead.
- **The campaign row collapses in a stated order**, each step a container query on the row (so a docked Hob panel narrows it the same way a phone does): below `@5xl` the world chip drops to its icon and the session badge goes; below `@3xl` the name goes (the chevron keeps the way home) and the tabs tighten from 13px to 10px a side; below `@2xl` the press is its icon, with its label as the accessible name and tooltip; below `@xl` _Cast_ and _Chronicle_ move into a _More_ menu at the end of the tabs; below `@lg` _Party_ and _Notes_ join them, leaving _Overview_ and _Encounters_. Above `@3xl` a long name truncates first. A player's row (three tabs, no press) needs no step. `shell/TabRow.tsx` is the one collapsing tab row, also used by the Library's shelves and an NPC's tabs: each item names the step below which it leaves the row, and each band draws one _More_ holding exactly what that band hid, lit when the current page is in it. No chrome row is a scroll container; overflow there is a responsive-layout defect rather than another scrolling surface.
- The row's lead group (name, world chip, badge) is capped at `max-w-96` and the name truncates inside it; the tabs follow it at `ml-2`, so where they start follows the name.
- The global row is `@taverns/ui`'s `NavigationMenu` (Base UI's primitive, shadcn's port): _Campaigns_, whose panel holds _Campaigns_ and _Shared Worlds_; _Library_, whose panel holds every shelf; and _Characters_, a plain link. The same three in every build. The Library panel and the Library's own tab row both read `library/shelves.ts`, so they cannot list different shelves. Each panel is a featured panel: a decorative hero tile (a 4:1 banner picture, the item's name, a tagline; not a link, `alt=""`) across the top, above rows that carry a one-line description under their title, the title alone being the link's name and the line its `aria-describedby`. A shelf's description lives on its `SHELVES` entry, the Campaigns panel's beside its entries in `GlobalNav`. The panel is `w-md` capped at the positioner's `--available-width`, the same stack at every width. The pictures are `shell/heroes/`, made from the full-size originals (not committed) by `apps/web/scripts/nav-heroes.mjs` at the banner's 1x width and the 768px the originals allow.
- A panel's owner is a disclosure button, not a link that also opens a menu: one control cannot tell a screen reader whether a press navigates or discloses. The page it stands for is the first link in its panel, which is one pointer click away because panels open on hover. The keyboard walks the row with ←/→, opens a panel with Enter, Space or ↓, walks it with ↓/↑ or Tab, and Esc closes it and hands focus back to the trigger.
- A global item is lit by `useSection()` (a Shared World's screens light _Campaigns_, any shelf lights _Library_, a sheet lights _Characters_); a lit trigger carries `aria-current="true"`, and the panel's link for the page you are on carries `aria-current="page"`.
- The global row's controls are their icons below its `@2xl` (the wordmark goes first, at the same step), with the label kept for screen readers and the tooltip; a trigger keeps its chevron. Panels portal to the body on `z-popup`, capped at the room below the trigger, and scroll within themselves past that.
- Every control on the global row is the one 26px pill, _Ask Hob_ included, and _Ask Hob_ reflects the panel's open state (`aria-pressed`, accent-soft fill, accent border) because `useHobPanel` owns ⌘K and Esc and a button holding its own idea of open would be wrong the first time somebody used the keyboard.

**One peach primary per screen, at most.** The accent fill says "this is the next thing to do", and two of them say nothing. Inside a campaign that fill is the campaign row's press on every tab, so a tab's own create verb is `secondary` or `outline` in its header and a card's own verbs are `outline`. `shell/primaries.test.tsx` walks every screen the Playwright suite does (`test/screens.ts`) and counts `Button`'s default variant. Above a campaign, a screen's create verb is that primary in the bar, or in the hero on a Shared World's Overview, and opens a dialog (_New campaign_, _New Shared World_); the Campaigns screen founds no Shared World, since _Shared Worlds_ has its own place in the global row. A screen that breaks the budget is listed in the test's `overBudget` as an open defect, asserted to still be over, so fixing one fails the test until its line is deleted.

There is no global mode. Chrome derives from `useCampaignRelation` (`creator` or `player`, off the `GET /me/campaigns` row the campaign frame already holds), so one campaign URL renders creator chrome to its creator and participant chrome to a player. While the relation is unsettled the campaign row draws no items; a failed read falls back to `creator`, because a stranger seeing creator chrome over a `NotFound` discloses nothing while a player seeing it would. Ask Hob is absent for a player (`AskHobSlot`) because the docked panel's verbs are creator writes. A player's campaign row is the screens with player projections: Overview, Table, Chronicle, and it carries no badge, because a player's session read is visibility-gated.

## Measuring the shell

jsdom computes no layout, so the pixels are asserted by the Playwright suite, `pnpm -F web e2e` (`apps/web/e2e/README.md`). It runs Chromium over the fixture maps (`test/scenarios.ts`, served by a Vite plugin as a stub API), with no Postgres, no API server and no model or image calls, on every screen in `test/screens.ts` at 1440, 1024, 760 and 390. Each spec's header comment says what its checks guard and why; the rules they hold:

- Rows are 44 / 46 / 76 / 40 wherever the bar is not wrapping, the stack is `z-index` 10, and every global-row control is 26px. Inside a campaign the chrome is 91 (the two rows and the header's hairline) on every tab at every width, and every campaign screen's `main` top and `h1` y are one value, its header 48 tall from 896 up; the two Overviews are exempt from the last two because their `h1` is in the hero.
- `scrollWidth` equals `clientWidth`, no chrome row overflows, nothing in the chrome or a campaign header is drawn past its edge (the frame clips sideways, so `scrollWidth` cannot see that), and no two header controls overlap. After a 400px scroll the stack is at `top: 0` and on top, and no `sticky` in `main` pins under it. Nothing in `main` scrolls on its own outside a dialog.
- The first campaign tab starts 8px (`ml-2`) after the lead group, the chevron is never squeezed, the lead never spills, and the press sits after the last tab.
- Each global panel, opened with a pointer and shut with Esc, is inside the viewport and on top, adds no width, has its hero decoded and every row inside it with a description, and returns focus to its trigger.
- Hob, walked from the Overview through Notes, Party, the runner, the Library and back, is the same panel and header node at every step and stays pressed. From 1020 up it is an inline column at y=0, the viewport's height, flush right, with the chrome ending where it starts, and it stays there while the document scrolls; below that it is the overlay and never covers the bar.
- Every Overview hero overlaps its cover only while there is a picture, never puts the actions on it, and reserves the actions' height for the description whether there is a pitch or not.

## Sign-in and the signed-out gate

Clerk is a prerequisite. `auth/AuthProvider.tsx` mounts `ClerkProvider` when `VITE_CLERK_PUBLISHABLE_KEY` is set and otherwise renders `ClerkRequired`, a notice saying what to configure, in place of the whole app. The browser has no other credential: machine tokens authenticate on the server for its tests and scripts, and no browser path pastes or stores one.

`marketing/SignedOutGate.tsx` is the root route's component. `useCredentialPresence` in `auth/credential.ts` answers `present | absent | unknown` from the hosted session; a configured provider reports `signedIn: false` while still deciding, and `unknown` renders neither page (an empty page-coloured frame) rather than flashing the homepage over the app. A sign-out needs no rule of its own: the session ends, the gate answers `absent`, and the homepage renders (`auth/signOut.test.tsx`).

`/join/$token` is exempt, checked by path before the credential so it never waits on a vendor: it previews an invitation before anyone has an account.

Tests stand in for Clerk with a `HostedSession` of their own. `renderAt` wraps every route in `TEST_SESSION` (`test/session.ts`: signed in, `configured: false`) outside any `wrap` a test passes, so a test's own `HostedSessionScope` wins; pass `"none"` only for tests about the gate or the join page. The Playwright layout suite does the same through `e2e/stub/StubAuthProvider.tsx`. `configured: false` is what keeps the vendor's chrome out: `SignInSurface` and `StartCta` check `configured` and `publishableKey()` both, because Clerk's components may only mount where its provider did. Clerk itself is exercised only by `pnpm -F web e2e:auth`.

## The shape every screen copies

- One `Resource` per screen with three states, and as many atoms underneath as writes want to refresh independently ([Web data](web-data.md)).
- Every creator campaign destination wears `campaign/CampaignChrome.tsx`: its bar, and the campaign-wide dialogs (settings, invites, finishing the night, and its Shared World, archive and delete). A screen needing more passes an `extra` atom, combined with the view through `AsyncResult.all`, rather than opening a second resource; `CampaignChromeSlots` has no `reload`. A resource that re-runs per keystroke (the Chronicle's search) stays its own so it cannot blank the frame.
- `useCampaignAct` (`campaign/act.tsx`) computes the campaign's press once, asking the session and the run separately: a live run, no session, or a night open with nothing on the table. The run is undefined in the last case too, which is what a two-way branch gets wrong. The campaign row's press calls it, and so does the frame for an encounter's _Run_; on the fight it would send you back to, the press is absent. Opening and finishing a night go through `session/start.ts` and `session/finish.ts`; see [Live session](live-session.md).
- Every Overview (both of a campaign's and a Shared World's) opens with `OverviewHero` (`campaign/OverviewParts.tsx`), which takes the cover, the meta line, the name and the description, and the actions as children; `campaign/CampaignHero.tsx` is it over a `Campaign`. It draws the cover at `--overview-cover-h`, its bottom 45% fading into the page, and the header (meta line, the name as the `h1`, the pitch at `--overview-pitch-w`, the outline actions) pulled up over it by `--overview-cover-overlap` and inset 24px. It overlaps only while the cover shows a picture, which the cover says with `data-picture` because a URL that fails to load is only found inside `HobCover`; with no cover, while Hob is drawing, or when the draw or the load failed, the header sits flat under it. A campaign's meta line is the party's name and _Since_ the month the campaign was made: the drawing's ruleset and schedule are left out, the first a constant and the second stored nowhere. A world's is its campaign and member counts and _Since_ the month it was made.
- The creator's Overview (`campaign/CampaignScreen.tsx`) is centred at `max-w-overview`, hero included so its left edge is the columns', and splits into a main column (_Next session_, _Last time_) and an aside (_Party_, _Recent notes_) by the redesign's own flex wrap, `basis-overview-main` beside `basis-overview-aside` (`local-tokens.css`), so the aside drops under the whole main column below 884px of content whatever narrows it. Its cards are summaries: _Party_ and _Recent notes_ rows open nothing, and each header's link (_Manage_, _All notes_, _All encounters_, _Read the chronicle_) is the way into the tab. _Next session_'s encounter rows are the exception: each opens its encounter selected on the Encounters tab (`?encounter=`), from anywhere on the row, with its _Edit_ and _Run_ lifted above the link. The prep checklist and _Finish the night_ live in _Next session_, or in the live banner while a fight is on the table, so a night opened here can be finished here. _Last time_ and the rows' _Ready_ / _Draft_ are the reads the Overview adds (`overviewExtraAtom`, its `extra`): the newest ended night's beats verbatim, since nothing stores a summary, and every encounter's prep (`encounterPrep.list`, the Encounters page's own atom).
- The Encounters tab (`campaign/EncountersScreen.tsx`) is the redesign's list beside a preview, centred at `max-w-overview` like the Overview (`CampaignChrome`'s `centred`, header included). The list and the preview (`EncounterPreview.tsx`) are the same flex wrap, `basis-encounters-list-min` capped at `max-w-encounters-list` beside `basis-encounters-pane`, so the preview drops under the list below 704px of content; stacked, choosing a row scrolls the preview into view. A row is a button that selects: the selection is the `encounter` search param, written with `replace` so _Back_ leaves the page, and falls back to the first row shown. Rows are grouped _On the table now_ / _Not yet played_ / _Played_ from the live run and `lastPlayed`; the rules are `encounterList.ts`. The preview is one pane of the encounter's own data (the row, its read-aloud notes, `encounterPrep.list` as the page's `extra`, and the encounter page's map and roster reads for the selection); a section with nothing behind it is not drawn, and its tactics are always _Running it_ because they are the DM's plan, not a record of the night. Nothing on it is peach. Rows, the preview and the Overview's _Next session_ rows say _Ready_ or _Draft_ (`campaign/ReadyBadge.tsx`) from `EncounterPrep.ready`, the DM's own word; a played encounter says when it was played instead.
- A player's Overview (`play/PlayerCampaignScreen.tsx`) is the same page over the player's own load (`play/load.ts`), never the creator's narrowed: `OverviewPage` is the layout both use, and the cards take an `audience`. Main column: _Last time_ from the newest shared ended night through `recap.readAsPlayer`, the NPCs they can talk to, and the shared notes in full (_Shared with you_). Aside: _Party_ over the seats `party.list` answers them (their own and the shared ones, so every row may show its AC and hit points), without _Manage_ (no Party tab) and without the count of players who have no character, which over a partial roster would be wrong; _Recent notes_ when anything is shared, whose _All notes_ is the in-page _Shared with you_ section because a player has no Notes tab. _Next session_ is the DM's prep and is not drawn.
- A Shared World's screen (`shared-world/SharedWorldScreen.tsx`) is the same `OverviewPage` over the world's one view (`shared-world/load.ts`). Main column: the campaign directory as compact cards, each opening its campaign from anywhere on its face when the reader creates or plays it and a plain unlinked card otherwise (a link to a 404 is worse than none), then _Story So Far_ with the three newest Chronicle entries, whose _Read the chronicle_ opens `/worlds/:worldId/chronicle` (`SharedWorldChronicleScreen.tsx`): the summary with its Hob draft, the composer and every entry, under an ordinary bar with a `BackLink` to the world. Aside: _Members_, the owner marked. It reads nothing the world screen did not already read.
- Do not render a field the API does not have; a stubbed `0` is worse than an absent line. Layout that depends on a column's width uses a container query, never a viewport breakpoint. `shell/ShellLayout.test.tsx` greps the shell for one and fails; what is left elsewhere is a dialog's `sm:max-w-*`.
- `Button` rendering an `<a>` needs `nativeButton={false}`; the accessible role stays `button`, so a test finds a button and reads its `href`.
- jsdom here has no `localStorage` at all. Readers tolerate `undefined` (`storage()` in `auth/credential.ts`); a test that needs one installs it.
- Archiving is one column and the archived shelf is a second URL, not a query parameter. `apps/web` never re-filters `archivedAt`; the affordances are read off the membership's `relation`.
- A campaign card on a list opens the campaign and carries no campaign controls; its Shared World, archive and delete are inside the campaign. A card whose owner has commands gets `ui/ActionsMenu.tsx`, an overflow button that `<Card linked>` lifts above the link overlay. A permanent delete is armed by typing the name (`ui/confirmName.tsx`, `ui/confirmsName.ts`), one gate for both kinds.

## Forms and authoring traps

`ui/form.tsx` and `campaign/EncounterBuilderScreen.tsx` are the worked examples. A form that writes two tables composes one `Effect`. Validate in the form as well as the contract: a payload the schema rejects never leaves the browser and arrives as the `invalid` tag, whose message is for whoever wrote the schema.

- **Encounters are written on a page, not in a dialog.** The encounter builder (`/encounters/new`, `/encounters/<id>/edit`) is a two-column form with a rail beside it that adds to it, which fits no modal at 390 or at 1440; every way into writing one (the list, the preview's _Edit_ and _Add creature_, the Overview's rows, the encounter page) links there, so there is one editor. It asks before leaving with unsaved changes (the router's `useBlocker`), lands on the list with the encounter selected, and a kind switch never deletes a creature: the creatures card stays for a challenge or a hazard while it has lines. It is creator-only through its read: a blank one reads the creator's prep list, so a player gets `NotFound`.
- `SaveFailure` renders in the `DialogFooter`, never at the end of the body: the body scrolls and a line below the fold is one nobody sees.
- `VisibilityField` is the only place a `dm`/`shared` control is written; off is `dm` and the payload says so. A child row the DM is not asked about omits the field so the column default applies.
- `Select.Value` renders the value, not a label; every `SelectValue` takes a function. Base UI's `Switch` puts its `id` on the hidden input, so drive the `role="switch"` span. A headless browser opens `Select` only by keyboard (ArrowDown, walk `[data-highlighted]`, Enter).
- `render()`'s return type is not nameable from an exported signature (TS2742 under pnpm's isolated layout); annotate shared helpers `: void`.
- Fixtures in `campaign/campaign.fixtures.tsx` are the JSON the server sends, never a `Partial<>`, so a renamed field fails a test rather than rendering `undefined`. `installStubServer()` is called once per file at module scope, for the `Context.Reference` reason in [Web data](web-data.md).
- A dialog is portalled to the body: a test whose `afterEach` wipes the body must call RTL's `cleanup()` first or React unmounts into nothing.

## Tabs, and the filter input standard

Tabs go on their own row below the header (`TopBar`'s `tabs` slot, a `@container`, drawn with `shell/TabRow.tsx`) and a tab's actions live inside its content, never beside the tabs. The campaign and global rows are navigation tiers, not tabs. `FilterBar`'s `actions` slot (`library/filters.tsx`) is the one in-content placement for a tab's write verb.

Every search/filter surface draws one control, `FilterInput` in `packages/ui/src/components/ui/filter-input.tsx`, over the grammar in `filter-input-model.ts` (separately tested). Free text is the search; a filter is a condition (facet, operator, values) drawn as a segmented pill, never a `key:value` token. Operators come from the facet's shape: enum `is`/`is any of`, plus `is none of` only where the facet declares `not: true`; range `is`/`is at least`/`is at most`/`is between`; a boolean flips its value. Match all/any (`matchToggle`) renders only where the consumer honours OR, which only a client-filtered list can (no screen asks for it since the Encounters tab moved to pills); a server-paged corpus can only AND its clauses, and a toggle or a `not` there would narrow a page and call it the list. The one exception is the Encounters tab, whose filter is the redesign's single-select kind pills (`Toggle`) and no search box, the captain's call.

The box is one line and content-sized (`w-fit`, a `field-sizing-content` input), growing up to the consumer's `max-w-*` (`FilterBox` sets `max-w-3xl`). The component sets no `max-w-*` of its own: `tw-theme.ts`'s merge config knows only the named container scale, so a component default and a consumer's class would both survive `tailwind-merge` and source order would pick the winner. At the limit the oldest pills collect into a `+N filters` popover chip; `visiblePillCount` fits against the box's computed `max-width`, never its `clientWidth`, and the input's `min-w-30` must equal `PILL_LAYOUT.inputReserve`. The combobox underneath is a Base UI port, not shadcn's `command` (that is `cmdk`, which is Radix; the lockfile stays Radix-free).

Consumers use `useFilterQuery` in `library/query.ts` for the value, the debounced `q`, and the `valuesOf`/`flagOf`/`rangeOf` readers. In jsdom the box is `getByRole("combobox", { name: "Search …" })`, a typed commit is `type:bea{Enter}`, and an open suggestion popup holds the accessibility tree: press Escape before reaching for anything outside it.

## The Chronicle: the round that lies

A carried fight is two runs, and `RecapRunLink` carries the other run's round at each end. Two `Int`s that mean different things, so swapping them compiles and reads plausibly. `chronicle/fight.ts` is the only place the sentences are worded:

| sentence                                             | round                        |
| ---------------------------------------------------- | ---------------------------- |
| "Paused at round N when the night ended"             | `run.round`, its own, frozen |
| "Session M picked it up, and it has reached round K" | `continuedInto.round`        |
| "Resumed from round N of session M"                  | `continuedFrom.round`        |

`fight.test.ts` uses a fixture where the two numbers differ (paused at 4, since reached 7); with equal numbers the assertion holds whichever the screen picked. The state comes from `run.endedReason`, never from `endedAt`, and `fightStory` is shared by the DM's and the player's Chronicle so there is one chance to get it right.

Three more rules: the spine loads and the recaps do not (`RecapBody` mounts only while its card is open, because a list must not cost one recap per night); a search answer carries its own `q` (`SearchAnswer.q`), because the box is debounced and a count beside the current text describes the wrong search; and the excerpt is plain text rendered as spans by `search.ts`'s `segments`, never as markup.

## The character sheet screen

`characters/sheet.ts` is the pure half and is separately tested, because everything decided in it is wrong silently. `sheetSections(sheet, writable)` decides what is drawn: a section appears when the document fills it or when there is somewhere to write, and the spine lists exactly the drawn ones. Sections nothing on the sheet can create stay content-driven, which is what keeps `writable` meaning something. Controls exist only where a write exists; `CharacterSheetScreen.test.tsx` enumerates every pressable thing.

- The spine and the narrow rail are one `nav` restyled by width, never two, or every section is in the accessibility tree twice. A press pins its section until the reader scrolls by hand. The rail is told from the spine by flex direction, not position, because a stuck element reports its stuck `offsetTop`.
- Keeping your place across a write is two layers: `useApiAtom` holds the last value through a refresh so the document never unmounts and the window keeps its scroll, and the lit section and last `scrollY` are held above the resource anyway. Any screen that both re-reads and holds view state has this trap; the old tabbed sheet threw the reader back to the first tab on every save.
- The sheet scrolls with the window. The sticky identity card, spine and rail pin at `top-(--chrome-height)`, and the scroll-spy's reading line is that height plus the rail's, so neither copies the chrome's variable height.
- Repeated visible labels need a disambiguating `aria-label`: `Edit ${what}` on section edit buttons, `${label} score` on the six score inputs. Ids are slugified (`SkillsDialog`), because `Sleight of Hand` is a valid label and an invalid selector.

## An encounter's board

The encounter page (`campaign/EncounterScreen.tsx`) is the whole of one encounter, opened from the Encounters preview's heading, and the creator's alone: its `extra` atom reads the map, which only the creator may read, so a player at a table where the encounter is shared still gets the whole page as `NotFound` rather than an encounter with the map missing.

- The grid is an SVG laid over the picture whose `viewBox` is the plane the map is measured in: the original picture's pixels, or the board itself when there is no picture (`battleMapPlane`). Both fill one box that takes the plane's aspect ratio, so which variant loaded never matters and no screen scales a coordinate by hand; the strokes are `non-scaling-stroke`. Where squares fall is `packages/api/src/BattleMap.ts` (`gridLines`, `cellRect`, `squareAt`, `cellPxForColumns`, `offsetWithinSquare`), which the grid adjustment and the play feature use rather than restating the arithmetic.
- `BattleMapBoard` draws a `BattleMapView`, the fields a saved map, a grid being adjusted and a fight's board share, so the runner's map band (`run/RunBoardBand.tsx`) is the same component over the fight's own grid.
- The wire says a picture is pending or present, never why one is absent (no setting line, images off, the budget, a refusal, a failed draw), so the page says only that there is none. While one is pending the page re-reads `reads.battleMap` alone through `useHobDrawingPolling`.

## The Hob panel surface

`hob/useHobPanel.ts` owns open state, `inline`, and the ⌘K/Esc handlers; `HOB_INLINE_MIN` is 1020 and `inline` is `!useIsMobile(HOB_INLINE_MIN)`, so there is one media query. Above it the panel is a 400px, viewport-tall sidebar beside the whole shell, bars included; below it a scrimmed overlay at `z-scrim`/`z-dialog` over the content under the bars. The persistent layout calls `useHobPanel({ initialOpen: false })` once, so nothing is requested until the panel opens, and the panel stays open across navigation and across campaigns. The shell's seam is two props, `onAskHob` and `panel`; a screen with an "ask Hob" control of its own calls `useShowHob()`.

- `Hob` reads its scope from the route (`useCampaignId`, `useSharedWorldId`): a campaign, a Shared World, or the account's own everywhere else; a player's campaign, or one whose relation is still settling, is no scope. Its starters come from `hob/suggestions.ts` ([Hob](hob.md)). `useHobConversation` resets the transcript and thread when the scope changes, so moving between campaigns swaps the thread and not the panel. `ScopedHob` takes the scope as a prop for tests.
- The two forms answer to two boxes in `hob/HobDock.tsx`. `HobFrame` is the app's row: the shell's column, then a `sticky top-0 h-screen self-start` slot the inline sidebar's `absolute inset-y-0` container measures against, which is what keeps it viewport-tall and pinned while the document scrolls. `HobRegion` is the positioned row under the chrome that the overlay portals into, published through `HobRegionContext`; the dock is the region's sibling, so the frame owns that context and the one region inside it attaches the ref. Never wrap `Hob` in a second `HobRegion` and never restate its classes: a second region takes the ref and sizes the overlay to itself, and a portal to `<body>` scrims the app's own bar.
- Nothing in the shell's column may take a percentage height: as a stretched flex item its height is definite, so `min-h-full` on the region meant the viewport _below_ the chrome, overflowed the frame by the chrome's height and let the document scroll past the pinned panel.
- The 400px is `--panel-chat-w` in `packages/ui/src/local-tokens.css`, bridged as `--spacing-chat-panel`; three elements need the same measurement.
- A flex column that scrolls shrinks its children: artifact cards carry `shrink-0`. A fixed-size `<img>` in a flex row stretches regardless, because preflight's `img { height: auto }` beats the attribute; `HobAvatar` states its height in CSS, and `CharacterPortrait` fills a plate its class sizes.
- Omit an optional key rather than sending `undefined`: `{ threadId: undefined }` reaches the server as `null`, which `Schema.optional` refuses.
