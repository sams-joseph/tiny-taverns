# Web screens

Routing, the shell, the signed-out gate, the shape every screen copies, the authoring and filter conventions, and the traps in the Chronicle, the character sheet and the Hob panel. Read this before adding a route, a screen, a dialog or a filter box. Reads and writes are [Web data](web-data.md); tokens, layering and motion are [Design system](design-system.md).

## Routing: real paths

The route table is TanStack Router's file-based routing: one file per route under `apps/web/src/routes/`, and `apps/web/src/router.ts` holds the one `createRouter`, on the browser history. Every route is a path (`/campaigns/<id>`, `/join/<token>`), and a `#fragment` is only an in-page anchor. The app ran on a hash history to keep the invitation token out of access logs; the maintainer decided on 2026-09-23 that clean URLs are worth that, since an invitation is single-use. The API still takes the token in a `POST` body, never its own request line.

- `routeTree.gen.ts` is generated from `routes/` by the router plugin in `apps/web/vite.config.ts` on every Vite start (dev, build, Vitest, both Playwright configs) and is committed, because `tsc` needs it. oxfmt ignores it; CI fails when a build leaves it changed, so commit the regenerated tree with the route file. The plugin is pinned to the version built on the installed `@tanstack/react-router`'s `router-core`; bump the two together or two cores install. Code splitting is off: the app is one chunk.
- A route file exports only `Route` and imports its screen from the feature directory; a component defined beside `Route` trips `react-refresh`. Shared decoders live in `routes/-params.ts` (the `-` keeps the generator from reading it as a route). A parent that exists to decode an id is a `route.tsx` with `params` and no component (`$campaignId`, `$worldId`, `$encounterId`, `$npcId`), so its children inherit the decoded id.
- An index route's id and `fullPath` end in `/` (`/_shell/campaigns/`, `/campaigns/`), while its `to` does not (`<Link to="/campaigns">`). A bare `x.tsx` beside an `x/` directory would become the parent of everything in it, which is why every index is `x/index.tsx`.

- Every non-file path must be served `index.html`. Vite's dev server and `vite preview` do it; a static host needs the rewrite `README.md` names, or a reload on a deep link is a 404. The router's `basepath` is Vite's `base` (`import.meta.env.BASE_URL`), so a subpath deployment is one setting.

- A bad id is a bad link, not a crash. Every branded id decodes in `params.parse`, which returns `false` for anything the product did not mint; the router rejects that candidate and keeps matching, and every legible level has a `$` splat child, so a truncated run link lands on its campaign. Do not throw: a throw becomes a `PathParamError` and a rendered apology.
- Every product route sits under the pathless layout route `_shell` (`shell/ShellLayout.tsx`); `/join/$token` sits under `_standalone`, the same shell without the Hob panel. A pathless id prefixes every child's id, so `useParams({ from })` and `RouteIds` say `/_shell/campaigns/$campaignId`, while `to`, `matchRoute` and `fullPath` are paths and do not.
- `remountDeps` is set on every route whose params name a different thing so nothing loaded for one survives into another. It remounts the leaf, never the layout. The campaign index deliberately has none; it is what everything else falls back to.
- A rendered `href` is the path under the basepath. An imperative absolute link goes through `router.history.createHref(router.buildLocation(…).publicHref)` resolved against `location.origin`, which is what carries the basepath; `buildLocation(…).href` does not. `campaign/InviteDialog.tsx` is the one caller; `routes.test.ts` pins the basepath and `campaign/invites.test.tsx` the whole link.
- `Link` spreads `aria-current="page"` on any prefix match and `activeProps={{}}` does not stop it. Nav items pass `activeOptions={{ exact: true }}` so the bar's own section rule decides what is lit (`navLinkProps` in `shell/AppShell.tsx`).
- In-page anchors are `<Link to="…" hash="…">`, so the anchor names its page and the router's `scrollRestoration: true` performs the scroll.

Testing: `src/test/renderRoute.tsx`'s `renderAt(path)` renders the real tree at a real URL on a real browser history, a fresh router and `RegistryProvider` per render, and must be awaited because the first match resolves inside a `Suspense`. Screens are not mountable on their own. `shell/AppShell.test.tsx` enumerates `Record<RouteIds<typeof routeTree>, string | undefined>`, so a new route does not compile until it has a URL, splats included.

## The shell: mounted once, two rows, one section

`shell/AppShell.tsx` draws a global row and a campaign row that exists exactly when the route names a campaign. `shell/ShellLayout.tsx` is its only mount, so the header, both rows, the bar's slot and the Hob panel are the same nodes across navigation; `shell/ShellLayout.test.tsx` pins that by node identity and fails if any other file imports `AppShell`. The two nav rows and, above any campaign, the per-screen bar share one sticky `z-chrome` stack, and `main` is a `@container`. The stack and `main` are one column of `HobFrame`, the app's full-height row; a docked Hob panel is the row's other column, so it narrows the bars along with the content instead of sitting under them.

- A screen reaches the shell at one point: `TopBar` (`shell/TopBar.tsx`), rendered first in the screen. Above any campaign it is portalled into a slot inside that sticky stack, the per-screen bar. **Inside a campaign there is no per-screen bar** (the captain's decision of 2026-09-23, from the Overview redesign): every campaign screen is a tab of one thing, the campaign row is the last chrome row there, and `TopBar` draws the same header in place, at the top of the content. The Overview, the creator's and a player's, is the one campaign screen with no `TopBar`: it is the campaign itself, so its `h1` is the campaign's name in its hero (below). A Shared World's screen is the one screen above a campaign with no bar, for the same reason: it is the world's Overview and its `h1` is the world's name in the same hero. It decides from the route, so no campaign screen can draw a bar its siblings lack; `shell/ShellLayout.test.tsx` walks every audited screen and asks where its `h1` landed. Nothing travels up as a prop, and the rows need no separately maintained `top` offsets. The header is `@taverns/ui`'s `PageHeader` in both placements (`placement="bar" | "content"`), so the title, the reserved lines and the wrap rule are one implementation.
- Screen actions are the header's (`TopBar`'s children), never a button right-aligned elsewhere in the body; a card's own verbs stay on the card. The way back to a parent screen is `BackLink` (a chevron and the destination's name, rendered into the router's `Link`), first in the header's actions; the campaign row's way home is the same component. On the creator's Overview the hero carries the campaign's management as outline buttons: _Invite player_, _Settings_ wearing the _Private_ / _Shared_ word (the prototype drops the word; the captain kept it), and _Campaign actions_; on a player's it carries their one verb, the peach _New character_. A Shared World's hero carries the peach _New campaign_ for every member (founding one is any member's act), and for its owner _Shared World settings_ and _Shared World actions_ (archive, delete) as outline buttons beside it.
- Every screen grows the document and the window scrolls, under the sticky chrome stack, except the runner's canvas (below). A page is never bounded to the viewport with its scrolling handed to an inner container: a second scroller is where the wheel gets stuck, and it hides content behind a scroll box nobody sees. `sticky` is fine, and pins under the chrome by `--chrome-height`, which `AppShell` measures off the stack and publishes on the document's root (the stack's height depends on the route; the root, so an overlay portalled to the body can sit under the chrome too). A modal dialog scrolling its own body is a separate case, and so is the Hob panel's thread. A chat on a page (`cast/RehearsalPanel.tsx`) is a transcript in the document with its composer `sticky` at the viewport's bottom, and keeps the newest line in view by scrolling the window to its end.
- "Nothing appears on both rows" is one value: `useSection()` in `shell/location.ts` answers a single `Section` and both rows ask it, so being inside a campaign and no global item being lit are the same fact.
- The campaign row wears `tabsTriggerVariants` (exported from `@taverns/ui` for this; do not copy the recipe); the global row is `navPillVariants`, kept beside it in `tabs.tsx`. An underline says which part of this campaign you are reading.
- Each row is its own `@container`: each runs out of room at a different width, and the question is whether this row fits. The page edge is the one question that is not a row's — every row and `main` ask `@container/app` on the shell's column (the frame less any docked Hob panel), so the nav rows and the content below them cannot pick different edges. **A container query resolves against the container's content box**, so a container that also carries the page padding makes every threshold inside it mean "that, plus 64px"; the rows put the padding on a box inside the container for this reason.
- The campaign name gives way whole (`hidden` under the row's `@3xl`) and the chevron keeps `min-w-4` as a floor so the way home survives; its `aria-label` carries the name plus "home" for the state where the name is not drawn.
- The campaign row sources itself: the way home from the route, the name from `campaignAtom`, and, for a creator only, the session badge from `campaignNightAtom` (the campaign, its open session and its live run, without the rest of the view). `campaign/campaignRow.test.tsx` reads the destinations out of the rendered row and visits each.
- Every row has a fixed height, written down in `AppShell.tsx`: 44 global, 46 campaign, 76 per-screen bar, 40 tab strip. This is a decision, not a minimum: the bar measured 61 / 89 / 141 between sibling tabs when it grew with its contents, so the content jumped as a DM changed tab. Inside a campaign the chrome is the two nav rows and nothing else, so every tab's content starts at one y at every width. The header reserves the subtitle line whether or not a screen has one and, from the `@4xl/app` container (896px) up, never wraps, so whatever follows it starts at one y across a campaign's tabs too. Below it the actions take their own wrapping row and the header's height follows the screen: at 390 and 760 the unwrapping row drew the Cast's controls on top of one another, and wrapping keeps the tap targets whole. A screen whose controls do not fit one row above the breakpoint simplifies its composition rather than shrinking them: a search box belongs on a filter row in the body (the Cast, Notes), not in the header. The delivered `base.css` gives every `p` a 12px bottom margin, which is why the subtitle carries `mb-0`. `shell/ShellLayout.test.tsx` pins the classes; the pixels are in [Measuring the shell](#measuring-the-shell).
- The campaign's one verb — _Start session_ / _Start an encounter_ / _Back to the fight_ — is the peach press at the right end of the campaign row, on every tab, as the redesign draws it (`CampaignAct` in `shell/AppShell.tsx`, sourced from the route like the rest of the row). It is the creator's only, it is absent on the fight it would send you back to, and it is absent on three screens whose own peach is their next step: one encounter's page, whose _Run_ is the same `run` aimed at that encounter, and two flows whose way out is _Cancel_ — the encounter builder (new and editing) and the campaign's character create form. The Overview's cards draw no second one: the live banner carries _Finish the night_ and leaves the way back to the row. It was once moved off this row because it overflowed at 760; the captain chose the row anyway, so the row collapses to make room instead.
- **The creator's campaign row is Overview, Encounters, Party, Cast, Notes, Chronicle**, the redesign's order. **It collapses in a stated order**, each step a container query on the row (so a docked Hob panel narrows it the same way a phone does): below `@5xl` the world chip drops to its icon and the session badge goes; below `@3xl` the name goes (the chevron keeps the way home) and the tabs tighten from 13px to 10px a side; below `@2xl` the press is its icon, with its label as the accessible name and tooltip; below `@xl` _Cast_ and _Chronicle_ move into a _More_ menu at the end of the tabs; below `@lg` _Party_ and _Notes_ join them, leaving _Overview_ and _Encounters_. Above `@3xl` a long name truncates first. A player's row (three tabs, no press) needs no step. `shell/TabRow.tsx` is the one collapsing tab row, also used by the Library's shelves and an NPC's tabs: each item names the step below which it leaves the row, and each band draws one _More_ holding exactly what that band hid, lit when the current page is in it. No chrome row is a scroll container; overflow there is a responsive-layout defect rather than another scrolling surface.
- The row's lead group (name, world chip, badge) is capped at `max-w-96` and the name truncates inside it; the tabs follow it at `ml-2`, so where they start follows the name.
- The global row is `@taverns/ui`'s `NavigationMenu` (Base UI's primitive, shadcn's port): _Campaigns_, whose panel holds _Campaigns_ and _Shared Worlds_; _Library_, whose panel holds every shelf; and _Characters_, a plain link. The same three in every build. The Library panel and the Library's own tab row both read `library/shelves.ts`, so they cannot list different shelves. Each panel is a featured panel: a decorative hero tile (a 4:1 banner picture, the item's name, a tagline; not a link, `alt=""`) across the top, above rows that carry a one-line description under their title, the title alone being the link's name and the line its `aria-describedby`. A shelf's description lives on its `SHELVES` entry, the Campaigns panel's beside its entries in `GlobalNav`. The panel is `w-md` capped at the positioner's `--available-width`, the same stack at every width. The pictures are `shell/heroes/`, made from the full-size originals (not committed) by `apps/web/scripts/nav-heroes.mjs` at the banner's 1x width and the 768px the originals allow.
- A panel's owner is a disclosure button, not a link that also opens a menu: one control cannot tell a screen reader whether a press navigates or discloses. The page it stands for is the first link in its panel, which is one pointer click away because panels open on hover. The keyboard walks the row with ←/→, opens a panel with Enter, Space or ↓, walks it with ↓/↑ or Tab, and Esc closes it and hands focus back to the trigger.
- A global item is lit by `useSection()` (a Shared World's screens light _Campaigns_, any shelf lights _Library_, a sheet lights _Characters_); a lit trigger carries `aria-current="true"`, and the panel's link for the page you are on carries `aria-current="page"`.
- The global row's controls are their icons below its `@2xl` (the wordmark goes first, at the same step), with the label kept for screen readers and the tooltip; a trigger keeps its chevron. Panels portal to the body on `z-popup`, capped at the room below the trigger, and scroll within themselves past that.
- Every control on the global row is the one 26px pill, _Ask Hob_ included, and _Ask Hob_ reflects the panel's open state (`aria-pressed`, accent-soft fill, accent border) because `useHobPanel` owns ⌘K and Esc and a button holding its own idea of open would be wrong the first time somebody used the keyboard.

**One peach primary per screen, at most.** The accent fill says "this is the next thing to do", and two of them say nothing. Inside a campaign that fill is the campaign row's press on every tab, so a tab's own create verb is `secondary` or `outline` in its header and a card's own verbs are `outline`. `shell/primaries.test.tsx` walks every screen the Playwright suite does (`test/screens.ts`) and counts `Button`'s default variant. Above a campaign, a screen's create verb is that primary in the bar, or in the hero on a Shared World's Overview, and opens a dialog (_New campaign_, _New Shared World_); the Campaigns screen founds no Shared World, since _Shared Worlds_ has its own place in the global row. A screen that breaks the budget is listed in the test's `overBudget` as an open defect, asserted to still be over, so fixing one fails the test until its line is deleted.

There is no global mode. Chrome derives from `useCampaignRelation` (`creator` or `player`, off the `GET /me/campaigns` row the campaign frame already holds), so one campaign URL renders creator chrome to its creator and participant chrome to a player. While the relation is unsettled the campaign row draws no items; a failed read falls back to `creator`, because a stranger seeing creator chrome over a `NotFound` discloses nothing while a player seeing it would. Ask Hob is absent for a player (`AskHobSlot`) because the docked panel's verbs are creator writes. A player's campaign row is the screens with player projections: Overview, Table, Chronicle, and it carries no badge, because a player's session read is visibility-gated.

## Measuring the shell

jsdom computes no layout, so the pixels are asserted by the Playwright suite, `pnpm -F web e2e` (`apps/web/e2e/README.md`). It runs Chromium over the fixture maps (`test/scenarios.ts`, served by a Vite plugin as a stub API), with no Postgres, no API server and no model or image calls, on every screen in `test/screens.ts` at 1440, 1024, 760 and 390. Each spec's header comment says what its checks guard and why; the rules they hold:

- Rows are 44 / 46 / 76 / 40 wherever the bar is not wrapping, the stack is `z-index` 10, and every global-row control is 26px. Inside a campaign the chrome is 91 (the two rows and the header's hairline) on every tab at every width, and every campaign screen's `main` top and `h1` y are one value, its header 48 tall from 896 up; the two Overviews are exempt from the last two because their `h1` is in the hero.
- `scrollWidth` equals `clientWidth`, no chrome row overflows, nothing in the chrome or a campaign header is drawn past its edge (the frame clips sideways, so `scrollWidth` cannot see that), and no two header controls overlap. After a 400px scroll the stack is at `top: 0` and on top, and no `sticky` in `main` pins under it. Nothing in `main` scrolls on its own outside a dialog and the runner's canvas.
- The first campaign tab starts 8px (`ml-2`) after the lead group, the chevron is never squeezed, the lead never spills, and the press sits after the last tab.
- Each global panel, opened with a pointer and shut with Esc, is inside the viewport and on top, adds no width, has its hero decoded and every row inside it with a description, and returns focus to its trigger.
- Hob, walked from the Overview through Notes, Party, the runner, the Library and back, is the same panel and header node at every step and stays pressed. From 1020 up it is an inline column at y=0, the viewport's height, flush right, with the chrome ending where it starts, and it stays there while the document scrolls; below that it is the overlay and never covers the bar.
- Every Overview hero overlaps its cover only while there is a picture, never puts the actions on it, and reserves the actions' height for the description whether there is a pitch or not.

## Sign-in and the signed-out gate

Clerk is a prerequisite. `auth/AuthProvider.tsx` mounts `ClerkProvider` when `VITE_CLERK_PUBLISHABLE_KEY` is set and otherwise renders `ClerkRequired`, a notice saying what to configure, in place of the whole app. The browser has no other credential: machine tokens authenticate on the server for its tests and scripts, and no browser path pastes or stores one.

The gate is the root route's `beforeLoad` (`routes/__root.tsx`), which answers `presence` as router context: `exempt` when a matched route declares `staticData: { rendersSignedOut: true }` (only `/join/$token`, which previews an invitation before anyone has an account, so it is checked first and never waits on a vendor), otherwise `present | absent | unknown` from the published hosted session (`routerAuth` and `presenceOf` in `auth/credential.ts`). `marketing/SignedOutGate.tsx`, the root's component, draws it: `unknown` is an empty page-coloured frame rather than the homepage flashed over the app, since a configured provider reports `signedIn: false` while still deciding; `absent` is the homepage in place at whatever URL was asked for, with no redirect, so a deep link survives Clerk's modal sign-in.

The `beforeLoad` decides synchronously and must not await the vendor: that makes the first load a Suspense fallback, and React throttles the reveal after one (`FALLBACK_THROTTLE_MS`, 300ms), so the signed-out homepage arrived a visible beat late. The router does not hear the session change, so `RoutedApp` (`App.tsx`) invalidates it whenever presence flips; a sign-in, a sign-out or the vendor's first answer re-runs the gate with no reload (`auth/signOut.test.tsx`). Child `beforeLoad`s and loaders still run while the answer is `unknown` or `absent`, and none exist; one that reads account data should wait on `presence` in `_shell`'s `beforeLoad`. The gate is not an access check: a creator-only screen is `campaign/CreatorOnly.tsx`'s, in its component, and the server's `NotFound` is the refusal.

Tests stand in for Clerk with a `HostedSession` of their own. `renderAt` wraps every route in `TEST_SESSION` (`test/session.ts`: signed in, `configured: false`) outside any `wrap` a test passes, so a test's own `HostedSessionScope` wins; `"none"` is nobody signed in, and a `HostedSession` is where a gate test starts. `renderAt` publishes that session before the router's first load, because the gate reads the slot rather than a `wrap`'s scope, and it renders `RoutedApp` so a changed session re-runs the gate. The Playwright layout suite does the same through `e2e/stub/StubAuthProvider.tsx`. `configured: false` is what keeps the vendor's chrome out: `SignInSurface` and `StartCta` check `configured` and `publishableKey()` both, because Clerk's components may only mount where its provider did. Clerk itself is exercised only by `pnpm -F web e2e:auth`.

## The shape every screen copies

- One `Resource` per screen with three states, and as many atoms underneath as writes want to refresh independently ([Web data](web-data.md)).
- Every creator campaign destination wears `campaign/CampaignChrome.tsx`: its bar, and the campaign-wide dialogs (settings, invites, finishing the night, and its Shared World, archive and delete). A screen needing more passes an `extra` atom, combined with the view through `AsyncResult.all`, rather than opening a second resource; `CampaignChromeSlots` has no `reload`. A resource that re-runs per keystroke stays its own so it cannot blank the frame.
- `useCampaignAct` (`campaign/act.tsx`) computes the campaign's press once, asking the session and the run separately: a live run, no session, or a night open with nothing on the table. The run is undefined in the last case too, which is what a two-way branch gets wrong. The campaign row's press calls it, and so does the frame for an encounter's _Run_; on the fight it would send you back to, the press is absent. Opening and finishing a night go through `session/start.ts` and `session/finish.ts`; see [Live session](live-session.md).
- Every Overview (both of a campaign's and a Shared World's) opens with `OverviewHero` (`campaign/OverviewParts.tsx`), which takes the cover, the meta line, the name and the description, and the actions as children; `campaign/CampaignHero.tsx` is it over a `Campaign`. It draws the cover at `--overview-cover-h`, its bottom 45% fading into the page, and the header (meta line, the name as the `h1`, the pitch at `--overview-pitch-w`, the outline actions) pulled up over it by `--overview-cover-overlap` and inset 24px. It overlaps only while the cover shows a picture, which the cover says with `data-picture` because a URL that fails to load is only found inside `HobCover`; with no cover, while Hob is drawing, or when the draw or the load failed, the header sits flat under it. A campaign's meta line is the party's name and _Since_ the month the campaign was made: the drawing's ruleset and schedule are left out, the first a constant and the second stored nowhere. A world's is its campaign and member counts and _Since_ the month it was made.
- The creator's Overview (`campaign/CampaignScreen.tsx`) is centred at `max-w-overview`, hero included so its left edge is the columns', and splits into a main column (_Next session_, _Last time_) and an aside (_Party_, _Recent notes_) by the redesign's own flex wrap, `basis-overview-main` beside `basis-overview-aside` (`local-tokens.css`), so the aside drops under the whole main column below 884px of content whatever narrows it. Its cards are summaries: _Party_ rows open nothing, and each header's link (_Manage_, _All notes_, _All encounters_, _Read the chronicle_) is the way into the tab. _Next session_ lists what is still to be played in the order the night reaches it (`onDeckOf`): the fight on the table, a carried one, then the DM's order from the Encounters tab, which the card shows and never sets; its opening read-aloud is the first of those rows'. _Next session_'s encounter rows and _Recent notes_ rows are the exceptions: each opens its object selected on its tab (`?encounter=`, `?note=`), from anywhere on the row, with an encounter row's _Edit_ and _Run_ lifted above the link. The prep checklist and _Finish the night_ live in _Next session_, or in the live banner while a fight is on the table, so a night opened here can be finished here. With no night open the card is the planned nights', when there are any: titled for the earliest, which _Start the night_ opens, and listing each in number order with its checklist and a confirmed _Delete this night_ that takes the checklist and keeps any act starting there ([Live session](live-session.md)), and no _Finish the night_; a started night has no delete here. _Last time_ and the rows' _Ready_ / _Draft_ are the reads the Overview adds (`overviewExtraAtom`, its `extra`): the newest ended night's summary when the DM wrote one, otherwise its beats verbatim, and every encounter's prep (`encounterPrep.list`, the Encounters page's own atom).
- The Encounters tab (`campaign/EncountersScreen.tsx`) is the redesign's list beside a preview, centred at `max-w-overview` like the Overview (`CampaignChrome`'s `centred`, header included). The list and the preview (`EncounterPreview.tsx`) are the same flex wrap, `basis-encounters-list-min` capped at `max-w-encounters-list` beside `basis-encounters-pane`, so the preview drops under the list below 704px of content; stacked, choosing a row scrolls the preview into view. A row is a button that selects: the selection is the `encounter` search param, written with `replace` so _Back_ leaves the page, and falls back to the first row shown. Rows are grouped _On the table now_ / _Not yet played_ / _Played_ from the live run and `lastPlayed`; the rules are `encounterList.ts`. _Not yet played_ is in the DM's planned order, the list's own, and is the one place that order is set: each of its rows has a grip handle, a sibling of the row's button, whose menu moves it to the top, up, down or to the bottom. A move is relative (`encounters.move`, before or after another encounter, never a position), and its anchors are the rows drawn, so under a kind pill it moves among what the DM can see and the hidden rows keep their places. `useEncounterOrder` (`campaign/encounterOrder.ts`) lays the move over the list at once until the list reads it back, and holds the next move until then; it drops the move on a refusal; focus goes back to the handle and a polite live region says where the row went. A pointer can also drag the grip (`campaign/encounterDrag.ts`, on `@dnd-kit/react`): the grip alone picks a row up, so the rest of the row still selects, and it alone takes no pan (`touch-none`), so a finger elsewhere still scrolls the window. A mouse drags after a few pixels and a finger after the library's long press; a click or tap opens the menu instead, which stays the keyboard's, the screen reader's and the fallback phone path. A drop lands before or after the nearest row drawn and goes through the same `useEncounterOrder` move. The library's `Feedback` plugin is left out, because it lifts the row into the top layer, injects `z-index: calc(infinity)` and animates on its own 250ms. Instead, the carried row waits in place, dimmed; a drop line in the focus ring's colour marks the gap; and the dropped row slides to its new place on `transition-settle` (the motion tokens, so reduced motion makes it instant) on the `lifted` rung. The other groups are ordered by what happened, so they draw no handle but keep its gutter, and every name starts at one edge. The preview is one pane of the encounter's own data (the row, its read-aloud notes, `encounterPrep.list` as the page's `extra`, and the encounter page's map and roster reads for the selection); a section with nothing behind it is not drawn, and its tactics are always _Running it_ because they are the DM's plan, not a record of the night. The battle map is a 24:9 strip under the preview's header for every kind, linked to the encounter's page; the drawing's empty _Drop a battle map_ slot is not drawn, so with no picture there is no strip, and while Hob is drawing it says so and re-reads the map. Nothing on it is peach. Rows, the preview and the Overview's _Next session_ rows say _Ready_ or _Draft_ (`campaign/ReadyBadge.tsx`) from `EncounterPrep.ready`, the DM's own word; a played encounter says when it was played instead.
- An encounter is played once ([Live session](live-session.md)), so every press that starts one asks `playthroughOf` (`campaign/encounterList.ts`): only an encounter never played offers _Run_ (the preview, the Overview's _Next session_ rows, the encounter's page) or appears in `StartRunDialog`'s choice; a played one offers _View log_ (from the Encounters preview it opens the night it was played on the Chronicle, `?session=`; from the encounter's page and the Overview's rows, the run's log); one a night finished over offers _Pick up_ (`campaign/PickUpRunDialog.tsx`, `useCampaignAct`'s `pickUp`), which calls `runs.resume` and opens a night on the way as `StartRunDialog` does, but only while nothing is on the table. A fight on the table keeps its _Back to the fight_.
- The Party tab (`party/PartyScreen.tsx`) is the redesign's card grid, centred at `max-w-overview`, over the frame's `party.list`. ## Forms and authoring traps

`ui/form.tsx` and `campaign/EncounterBuilderScreen.tsx` are the worked examples. A form that writes two tables composes one `Effect`. Validate in the form as well as the contract: a payload the schema rejects never leaves the browser and arrives as the `invalid` tag, whose message is for whoever wrote the schema.

- **Encounters are written on a page, not in a dialog.** The encounter builder (`/encounters/new`, `/encounters/<id>/edit`) is a two-column form with a rail beside it that adds to it, which fits no modal at 390 or at 1440; every way into writing one (the list, the preview's _Edit_ and _Add creature_, the Overview's rows, the encounter page) links there, so there is one editor. It asks before leaving with unsaved changes (the router's `useBlocker`), lands on the list with the encounter selected, and a kind switch never deletes a creature: the creatures card stays for a challenge or a hazard while it has lines. The setting line sits in a _Battle map_ card under the details, below the picture Hob drew from it when there is one; the drawing's drop target is not drawn, because a map is drawn once, as the encounter is made, with no upload and no redraw. It is creator-only through its read: a blank one reads the creator's prep list, which the server refuses a player. Its rail's difficulty card rates the draft with `encounterDifficulty`, the helper the server rates the saved row with, over the levels of the seats `party.list` answers, which are the seats the server counts, so the card before a save and the list after it cannot disagree; the card alone is sticky, and only while the rail stands beside the form.
- **Notes save as you type; everything else saves on a press.** The captain chose the drawing's in-place writing for the Notes pane, and `campaign/noteAutosave.ts` is the whole of it: typing is debounced (`AUTOSAVE_DELAY_MS`), a discrete change, a blur, choosing another note and leaving the tab save at once, one note never has two requests in flight (later edits coalesce into the next PATCH), and a PATCH carries only the changed fields. `NoteUpdate.title` is non-empty, so an emptied title is held back while the rest saves, and the pane says so. There is no _Save_ and no leave guard; the pane shows _Saving…_ / _Saved_ / _Couldn't save_ with _Retry_. _New note_ therefore creates an _Untitled note_ at once (DM-only) and selects its title in the pane.
- `SaveFailure` renders in the `DialogFooter`, never at the end of the body: the body scrolls and a line below the fold is one nobody sees.
- `VisibilityField` is the only place a `dm`/`shared` control is written; off is `dm` and the payload says so. A child row the DM is not asked about omits the field so the column default applies. An NPC is shared from its drawer on the Cast (`cast/NpcDrawer.tsx`) or its page's _Edit_ dialog (`cast/NpcDialog.tsx`), the one way a campaign NPC reaches its players; the sentence names the whole public persona, since that is what `PlayerNpc` carries, not only what a player's screen draws.
- `Select.Value` renders the value, not a label; every `SelectValue` takes a function. Base UI's `Switch` puts its `id` on the hidden input, so drive the `role="switch"` span. A headless browser opens `Select` only by keyboard (ArrowDown, walk `[data-highlighted]`, Enter).
- `render()`'s return type is not nameable from an exported signature (TS2742 under pnpm's isolated layout); annotate shared helpers `: void`.
- Fixtures in `campaign/campaign.fixtures.tsx` are the JSON the server sends, never a `Partial<>`, so a renamed field fails a test rather than rendering `undefined`. `installStubServer()` is called once per file at module scope, for the `Context.Reference` reason in [Web data](web-data.md).
- A dialog is portalled to the body: a test whose `afterEach` wipes the body must call RTL's `cleanup()` first or React unmounts into nothing.

## Tabs, and the filter input standard

Tabs go on their own row below the header (`TopBar`'s `tabs` slot, a `@container`, drawn with `shell/TabRow.tsx`) and a tab's actions live inside its content, never beside the tabs. The campaign and global rows are navigation tiers, not tabs. `FilterBar`'s `actions` slot (`library/filters.tsx`) is the one in-content placement for a tab's write verb.

Every search/filter surface draws one control, `FilterInput` in `packages/ui/src/components/ui/filter-input.tsx`, over the grammar in `filter-input-model.ts` (separately tested). Free text is the search; a filter is a condition (facet, operator, values) drawn as a segmented pill, never a `key:value` token. Operators come from the facet's shape: enum `is`/`is any of`, plus `is none of` only where the facet declares `not: true`; range `is`/`is at least`/`is at most`/`is between`; a boolean flips its value. Match all/any (`matchToggle`) renders only where the consumer honours OR, which only a client-filtered list can (no screen asks for it since the Encounters tab moved to pills); a server-paged corpus can only AND its clauses, and a toggle or a `not` there would narrow a page and call it the list. There are four exceptions, all the captain's call: the Encounters tab, whose filter is the redesign's single-select kind pills (`Toggle`) and no search box; the encounter builder's bestiary (`campaign/CreaturePicker.tsx`, which an NPC sheet's _Start from a bestiary NPC_ also picks from, narrowed to humanoids), a `FilterInput` for text beside four single-select CR-band pills that send `crMin`/`crMax`, as drawn, where a CR range condition would take four presses to say one band; and the Notes tab (`campaign/NotesScreen.tsx`), the bestiary's shape: a `FilterInput` for text above single-select category pills (_All_ and the five categories), ANDed in the browser; and the Cast (`cast/CastScreen.tsx`), a `FilterInput` for text beside two single-select pill groups, _Everyone_ / _Met_ / _Not met yet_ (always one lit) and _Friendly_ / _Indifferent_ / _Hostile_ (the lit one clears), all ANDed in the browser, as drawn.

The box is one line and content-sized (`w-fit`, a `field-sizing-content` input), growing up to the consumer's `max-w-*` (`FilterBox` sets `max-w-3xl`). The component sets no `max-w-*` of its own: `tw-theme.ts`'s merge config knows only the named container scale, so a component default and a consumer's class would both survive `tailwind-merge` and source order would pick the winner. At the limit the oldest pills collect into a `+N filters` popover chip; `visiblePillCount` fits against the box's computed `max-width`, never its `clientWidth`, and the input's `min-w-30` must equal `PILL_LAYOUT.inputReserve`. The combobox underneath is a Base UI port, not shadcn's `command` (that is `cmdk`, which is Radix; the lockfile stays Radix-free).

Consumers use `useFilterQuery` in `library/query.ts` for the value, the debounced `q`, and the `valuesOf`/`flagOf`/`rangeOf` readers. In jsdom the box is `getByRole("combobox", { name: "Search …" })`, a typed commit is `type:bea{Enter}`, and an open suggestion popup holds the accessibility tree: press Escape before reaching for anything outside it.

## The Chronicle

The Chronicle (`chronicle/ChronicleScreen.tsx`, and `PlayerChronicleScreen.tsx` through the same `SessionEntry`, `NightBody` and `ChronicleParts.tsx`) is the redesign's list of nights under their acts beside _Jump to_, centred at `max-w-overview`. The rules that are not visible in the code's shape:

- **A night's title is only what the DM typed**, otherwise "Session N". The drawing names a new night after its first encounter; a Shared World is told a night's title whatever its own switch says ([Shared Worlds](shared-worlds.md)), so a derived title would tell other tables the name of an encounter this table's players were never shown.
- **An opened night leads with the DM's summary, then its beats and its runs, split by who may read them.** The summary is on the session row, above the detail and never instead of it. A beat shared with the table is a bullet; one kept back is in the _DM only_ box. A player's recap holds only the shared beats, so the box never draws there. Each run is a chip with its kind's glyph (`KIND_ICON`); the DM's opens the encounter (`?encounter=`) while it still exists, and a player's is plain text carrying the name the server sent, which is neutral unless the encounter is Shared and Ready.
- **Writing a night up is a card above the nights, for the newest played night (live or ended) while it has no summary** (`nightToWriteUp`); an older night is written up from inside its own card. Hob drafts and the DM keeps: _Ask Hob to draft_ asks with `intent: "nightSummary"` and the night (`summaryDraft.ts`) and only fills the box, and only while the box is empty or still holds Hob's words; _Add to chronicle_ accepts that turn, so the summary is stamped `assistant`, then `PATCH`es the title, the spotlight and any edit. Emptying the box drops the draft, so words the DM wrote from scratch are never stamped Hob's. With no model behind Hob the press is not drawn; whether there is one is read with the record (`loadChronicleSpine`), so the card above the nights cannot grow after a `?session=` link has scrolled. _Add_ is outline: the campaign press is the screen's one peach.
- **Everything that changes a written night is inside its opened card**, never on the closed header: _Edit_ (the same composer, inline), _Clear summary_ (asks first), _Share with the table_ (the session's `visibility`) and each moment's _Share_ / _Unshare_ (`beats.update`). A night starts `dm`, so a player's Chronicle is empty until its DM shares one; a shared night names whose night it was from the player's own `party.list`, which the server has already narrowed.
- **The record is one read.** `chronicle.read` (a player's `chronicle.readAsPlayer`) answers every night with its runs and beats, so a closed card can clamp the DM's summary to two lines (the night's length when none is written) and _Expand all_ opens every card without a request per night; the per-night recap stays the Overview's _Last time_. Any number of cards may be open; `?session=` opens that night alone and scrolls it under the chrome, so no card above it grows while it is being reached. Which cards are open sits above `CampaignChrome`, whose header holds _Expand all_, so the scroll runs from the component that draws the cards (`useLanding`): the frame mounts its body only after every read answers, and a scroll fired before that lands nowhere.
- **Acts group by arithmetic over what the reader was answered** (`chronicle/acts.ts`): a night falls in the act with the highest start at or below its number, nights older than every act have no heading, and an act holding none of the reader's nights is not drawn. A player is answered only shared acts, so a night in an act the DM kept back reads under the shared act before it; saying otherwise would need the hidden act's start. The heading is the title as typed, never a computed "Act II", because a player's count over shared acts would disagree with the DM's. _Start a new act here_ is inside an opened night that starts none; rename, share and remove (confirmed) are the heading's menu, the DM's only.
- **The story so far heads the nights and is read with them** (`StoryCard.tsx`, in the same load as the record), because a card that arrived later above the nights would push down the night a link had just landed. Hob drafts it and the DM keeps it: _Ask Hob to draft_ (offered only while a model answers, the spine's `hobAvailable`) opens the panel with the question already sent (`useAskHob`), and only _Keep_ in the panel writes. Kept, it is the DM's to edit, clear (asks first) and share (`VisibilityField`, off by default). _Update needed_ and the end of _Previously_ are one test: a night numbered above its `afterSessionNumber` has ended, since _Previously_ opens only the night after. A player reads it through `story.readAsPlayer`, only once shared, with none of the controls.
- **_Jump to_ is unbounded, not sticky, and absent once the columns stack**: it indexes the nights, and under them it would be a list of what the reader has just passed. It is drawn from `@4xl` of `main`, just above where `basis-overview-main` beside `basis-overview-aside` would wrap.
- **The Spotlight is the DM's balancing tool, not record**, so the player's aside has none. It counts each live seat's spotlit nights (`chronicle/spotlight.ts`); a retired seat is not a row, and "fewest" is marked and named only when the counts differ. It sits in the aside, so it goes with _Jump to_ once the columns stack.
- **What the drawing left off is gone**, by the maintainer's call: search, the fight and scene story cards, read-alouds, ticked prep, the _Read aloud_ toggle and _Threads still open_. A run's log is still one press from its encounter's page.

## Telling a fight: the round that lies

A carried fight is two runs, and `RecapRunLink` carries the other run's round at each end. Two `Int`s that mean different things, so swapping them compiles and reads plausibly. `chronicle/fight.ts` is the only place the sentences are worded, and the Overview's _Last time_ reads a night's fights through it:

| sentence                                             | round                        |
| ---------------------------------------------------- | ---------------------------- |
| "Paused at round N when the night ended"             | `run.round`, its own, frozen |
| "Session M picked it up, and it has reached round K" | `continuedInto.round`        |
| "Resumed from round N of session M"                  | `continuedFrom.round`        |

`fight.test.ts` uses a fixture where the two numbers differ (paused at 4, since reached 7); with equal numbers the assertion holds whichever the screen picked. The state comes from `run.endedReason`, never from `endedAt`, and `fightStory` is shared by the DM's and the player's _Last time_ so there is one chance to get it right.

A conversation, a skill challenge or a hazard (`run.mode`) takes no turns, so `fightStory` never tells one by a round, and a carried scene is "Resumed from session M" with no round. The DM's recap carries the scene (`RecapFight.scene`) and its log, so the DM reads a challenge made or lost against its own numbers, with the prep's _If they make it_ / _If it goes wrong_ line only when one was written, and a hazard by the stages it lasted, with the log counted in place of the initiative line. The player's recap has neither, and the same function tells a player the kind and that it ended (the captain's decision of 2026-09-25).

## The character sheet screen

`characters/sheet.ts` is the pure half and is separately tested, because everything decided in it is wrong silently. `sheetSections(sheet, writable, logged?)` decides what is drawn: a section appears when the document fills it or when there is somewhere to write, and the spine lists exactly the drawn ones. _Level ups_ is the one section with a source beside the document: `logged` says whether the level-up records give it something to draw: the owner's read (or a failure to read it) on the owner's sheet, the seat's `levelUps` on the seat page, and the document's own lines alone on an NPC's sheet. Sections nothing on the sheet can create stay content-driven, which is what keeps `writable` meaning something. Controls exist only where a write exists; `CharacterSheetScreen.test.tsx` enumerates every pressable thing. The document is one component, `characters/SheetDocument.tsx`, for the owner, for the creator's seat page and for an NPC's _Stats_ tab (`cast/NpcSheetPanel.tsx`). It takes the document (`DrawnSheet`: the rules half every sheet has, plus the player's half when there is one), not the character, and two optional halves: `edits`, the section edit buttons and the empty-section prompts, and `play`, the dice, spends and roll log, whose `owned` is what rolls and spends. The owner passes both; an NPC's sheet passes `edits` alone, because nothing rolls or spends for an NPC until it can take part in a fight; the seat page passes neither and `drawnSections(sheet, false, logged)`, and `party/SeatScreen.test.tsx` asserts there is nothing to press. An NPC's sheet has no player's half, so it never draws _Story_ or _Level ups_, even writable: _Story_ is drawn empty for writing only on a document that carries `notes`.

The abilities, skills, spell and gear dialogs are the character's and the NPC's alike. Each takes a `SheetTarget` (`characters/sheetTarget.ts`): the document, a whole-document `save` at the version read, the keys it writes and the spell list it picks from. `characterSheetTarget` is the owner's `/me` write and spell read; `npcSheetEditor` (`cast/npcSheet.ts`) is the NPC's sheet PATCH with the document and no identity column, so the server keeps the document as sent, and its `…/sheet/spells` read. The identity (level, class, the numbers) stays each screen's own dialog, since the character's columns and the NPC's differ; a level or class change there is the PATCH that recomputes the document.

- The spine and the narrow rail are one `nav` restyled by width, never two, or every section is in the accessibility tree twice. A press pins its section until the reader scrolls by hand. The rail is told from the spine by flex direction, not position, because a stuck element reports its stuck `offsetTop`.
- Keeping your place across a write is two layers: `useApiAtom` holds the last value through a refresh so the document never unmounts and the window keeps its scroll, and the lit section and last `scrollY` are held above the resource anyway. Any screen that both re-reads and holds view state has this trap; the old tabbed sheet threw the reader back to the first tab on every save.
- The sheet scrolls with the window. The sticky identity card, spine and rail pin at `top-(--chrome-height)`, and the scroll-spy's reading line is that height plus the rail's, so neither copies the chrome's variable height.
- Levelling up is a wizard over the sheet (`characters/LevelUpDialog.tsx`), and `characters/levelUp.ts` is its pure half. The offer is read beside the sheet rather than when the wizard opens, because it decides whether _Level up_ is drawn at all: no hit die (a class the rules do not resolve) or no next level (`Conflict`) and the Level box is the only path. The steps are only the parts the offer carries, and the review holds the payload to the offer with `levelUpChosen`, the write's own rule, so _Level up to N_ is never offered for a payload the server would refuse for a reason the client could know. The wizard is keyed on the offer's version: after a `Conflict`, _Reload_ re-reads the sheet and the offer, and a new version starts the steps over on the new offer. The Log merges the records with the document's older lines (`logEntries`) and offers _Undo_ on the latest record only while the character is at its level, behind a confirm; an undo that left a hand-changed score says so before the dialog closes. _Level up with Hob_, beside it and drawn under the same condition, is the level-up composer (`characters/HobLevelUpDialog.tsx`, `characters/levelUpDraft.ts`): it asks `/me/hob` with `intent: "levelUp"` and draws the proposal as the panel's card does (`hob/transcript.ts`'s `artifactFrom`), and _Keep it_ is the accept, naming `levelUpWrites` as the wizard's confirm does. The docked panel draws the same card read back from that thread, and its keep names the same keys from the roster's row the accept answers.
- Repeated visible labels need a disambiguating `aria-label`: `Edit ${what}` on section edit buttons, `${label} score` on the six score inputs. Ids are slugified (`SkillsDialog`), because `Sleight of Hand` is a valid label and an invalid selector.

## An encounter's board

The encounter page (`campaign/EncounterScreen.tsx`) is the whole of one encounter, opened from the Encounters preview's heading, and the creator's alone: its `extra` atom reads the map, which only the creator may read, so a player at a table where the encounter is shared cannot load the page at all rather than getting an encounter with the map missing. The server's refusal is the gate for every encounter route; what a player who types one reads is `creatorOnly` (`campaign/CreatorOnly.tsx`), chosen by the membership `relation` before any creator read, and the same at every URL so it says nothing about which encounters exist. Somebody with no seat still gets the refusal's `NotFound`.

- The grid is an SVG laid over the picture whose `viewBox` is the plane the map is measured in: the original picture's pixels, or the board itself when there is no picture (`battleMapPlane`). Both fill one box that takes the plane's aspect ratio, so which variant loaded never matters and no screen scales a coordinate by hand; the strokes are `non-scaling-stroke`. Where squares fall, and how far apart they are, is `packages/api/src/BattleMap.ts` (`gridLines`, `cellRect`, `squareAt`, `cellPxForColumns`, `offsetWithinSquare`; `feetBetween` and `reachableSquares` under either `DiagonalRule`, `areaSquares`, `rulerReading`), which the grid adjustment and the play feature use rather than restating the arithmetic.
- `BattleMapBoard` draws a `BattleMapView`, the fields a saved map, a grid being adjusted and a fight's board share, so the runner's battle map (`run/RunBoardCard.tsx`) is the same component over the fight's own grid, and so is a seated player's (`play/PlayerBoard.tsx`), which hands it `PlayerLiveBoard` with the setting and the pending flag absent rather than widening the player's type.
- The runner lays its tokens (`run/RunTokens.tsx`) in the same box as `cellRect`s in percentages of the plane, so a token's button is its whole square at any width. Its face (`run/TokenFace.tsx`) is drawn in the drawing's own 40-unit square and scaled to the square it stands on, with the design system's type and spacing inside a `foreignObject`, so the rings, the `HpBar` under it, the condition count and the name keep the drawing's proportions at any zoom without restating a measurement. A token nobody has put down waits in the tray and goes down on the square clicked once selected; nothing guesses it a square. The board takes a pointer only from `@3xl` of `main`, on the canvas, which never opens a square under the 24px a pointer target needs; below it the tokens are a second, `aria-hidden` layer with nothing to press or tab to, and the initiative strip selects. A placed token moves by a drag with a live ruler (`rulerReading`, against the mover's speed when it is their turn) or the arrow keys; a drop on a square another token holds is refused in the browser though the server would stack them, and a dropped token holds its square until the server answers the move, then stands where the server has it. While the creature whose turn it is stands selected, the squares the leading number of its stat block's or sheet's speed reaches are tinted (`reachableSquares`, less the held squares), absent when that is not a number. Distances use the campaign's `diagonalRule`, so the ruler, the range and the move line agree with the server's `feet_moved`. _Grid_ and _Names_ (which tokens wear their name, kept in this browser's storage behind a guard) are the DM's view, not writes. The runner's header carries _Share_ (the fight) and, for a fight with a board, _Share map_, disabled while the fight is not shared because it narrows _Share_ rather than replacing it; the board's _Hide from players_ is a write that takes every monster's token off the players' board and fades them on the DM's. All three name `reads.playerTable`. The player's board wears the DM's token face with nothing to press, and numbers two tokens of one name in the player's order, since the table sends no creation time.
- The wire says a picture is pending or present, never why one is absent (no setting line, images off, the budget, a refusal, a failed draw), so the page says only that there is none. While one is pending the page re-reads `reads.battleMap` alone through `useHobDrawingPolling`.

## The Hob panel surface

`hob/useHobPanel.ts` owns open state, `inline`, and the ⌘K/Esc handlers; `HOB_INLINE_MIN` is 1020 and `inline` is `!useIsMobile(HOB_INLINE_MIN)`, so there is one media query. Above it the panel is a 400px, viewport-tall sidebar beside the whole shell, bars included; below it a scrimmed overlay at `z-scrim`/`z-dialog` over the content under the bars. The persistent layout calls `useHobPanel({ initialOpen: false })` once, so nothing is requested until the panel opens, and the panel stays open across navigation and across campaigns. The shell's seam is two props, `onAskHob` and `panel`; a screen with an "ask Hob" control of its own calls `useShowHob()`, or `useAskHob()` when the control is a whole question: the panel holds it (`asked`) until its status has answered and nothing is in flight, then sends it, and closing the panel first withdraws it.

- `Hob` reads its scope from the route (`useCampaignId`, `useSharedWorldId`): a campaign, a Shared World, or the account's own everywhere else; a player's campaign, or one whose relation is still settling, is no scope. Its starters come from `hob/suggestions.ts` ([Hob](hob.md)). `useHobConversation` resets the transcript and thread when the scope changes, so moving between campaigns swaps the thread and not the panel. `ScopedHob` takes the scope as a prop for tests.
- The two forms answer to two boxes in `hob/HobDock.tsx`. `HobFrame` is the app's row: the shell's column, then a `sticky top-0 h-screen self-start` slot the inline sidebar's `absolute inset-y-0` container measures against, which is what keeps it viewport-tall and pinned while the document scrolls. `HobRegion` is the positioned row under the chrome that the overlay portals into, published through `HobRegionContext`; the dock is the region's sibling, so the frame owns that context and the one region inside it attaches the ref. Never wrap `Hob` in a second `HobRegion` and never restate its classes: a second region takes the ref and sizes the overlay to itself, and a portal to `<body>` scrims the app's own bar.
- Nothing in the shell's column may take a percentage height: as a stretched flex item its height is definite, so `min-h-full` on the region meant the viewport _below_ the chrome, overflowed the frame by the chrome's height and let the document scroll past the pinned panel.
- The conversations list (`hob/HobThreads.tsx`, the header's _Conversations_) is a sheet contained by the panel's own `section` (`SheetContent`'s `container`, which is why that section is `relative overflow-hidden`): it slides from the panel's left edge over three quarters of it, so inline it never covers the screen beside it and overlaid it stays inside the overlay. It is the sidebar's own arrangement one box in: non-modal, dismissed by its scrim, its close button or Escape, which the dialog consumes so `useHobPanel` leaves the panel open. It reads `threads` again each time it opens; picking a row abandons any answer in flight and reads that thread's turns in. `e2e/layout/hob-threads.spec.ts` measures the box.
- The 400px is `--panel-chat-w` in `packages/ui/src/local-tokens.css`, bridged as `--spacing-chat-panel`; three elements need the same measurement.
- A flex column that scrolls shrinks its children: artifact cards carry `shrink-0`. A fixed-size `<img>` in a flex row stretches regardless, because preflight's `img { height: auto }` beats the attribute; `HobAvatar` states its height in CSS, and `CharacterPortrait` fills a plate its class sizes.
- Omit an optional key rather than sending `undefined`: `{ threadId: undefined }` reaches the server as `null`, which `Schema.optional` refuses.
